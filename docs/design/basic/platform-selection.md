# 基盤の選定

- 状態：決定（実測は 2026-11-18 に完了。「実測の結果」を参照）
- 日付：2026-11-16
- 関係する要件：PRE-2, PRE-4, PRE-5, PRE-9, PRE-11, USR-1, SEC-3, SEC-4, SEC-5, RSV-23, RSV-24, LOG-6, NFR-2, NFR-3, NFR-4, NFR-5, FUT-1〜FUT-8, OPN-1

## 決定

**Cloudflare Workers の無料プラン（Workers Free）を使う。支払い方法（カード）は登録しない。**

| 役割 | 使うもの |
| --- | --- |
| サーバの処理 | Workers（JavaScript） |
| 画面 | Workers が配る静的ファイル（HTML / CSS / JavaScript） |
| データと排他 | Durable Objects（SQLite）。すべてのデータをここに置く（実測の結果 1） |
| 定期処理 | Cron Triggers（FUT-3 の控えなど。v0.1.0 では作らない） |
| テストとデプロイ | Vitest（`@cloudflare/vitest-plugin`）、wrangler、GitHub Actions |

## 前提

- 学校のアカウント（PRE-11）は未定。メールアドレスで外部サービスに登録できることだけを前提にする。
- GitHub（コードの置き場所と CI）は PRE-11 の対象外とする。この構成では GitHub が止まっても稼働中のシステムは止まらない（デプロイができなくなるだけ）。コードの原本とデプロイの経路が生徒のアカウントにあることは承知のうえとする（2026-11-17 に開発者が確認）。

## 要件ごとの満たし方

| 要件 | 満たし方 |
| --- | --- |
| PRE-2 | カードを登録しない無料プランでは課金が起きない。1日の上限を超えると処理がエラーになる（停止）。上限は 00:00 UTC（日本時間 9:00）にリセットされる |
| PRE-4 | 個人情報を Cloudflare に置く。要件上許される |
| PRE-5 | サーバも画面も JavaScript。Request / Response など Web 標準の API が中心。Cloudflare 固有の概念（Durable Object）は予約台帳の部分に閉じ込める |
| PRE-9 / NFR-5 | 使われないことを理由に停止する仕組みがない |
| PRE-11 | Cloudflare のアカウントを学校のアカウントで作り、Super Administrator とする。開発する生徒はメンバーとして招待する（全プランで可能） |
| USR-1 / RSV-24 | すべての読み書きが Worker を通る。DB に直接つながる口を外に出さない |
| RSV-23 | 予約台帳を1つの Durable Object に置き、書き込みを順に処理する。DO の SQLite は同期 API なので、読む→確かめる→書くの間に他の処理が割り込まない |
| SEC-2 | `*.workers.dev` は HTTPS のみ |
| SEC-3 | 試行の回数をサーバ側で数える（接続元 IP は `CF-Connecting-IP` で取れる）。値は別の設計文書で定める |
| SEC-4 | 管理者のパスワードと共有された情報は PBKDF2-SHA256（Web Crypto）でハッシュ化する。反復回数は実測で決めた（実測の結果 2）。※ 2026-11-16 追記：共有された情報は台帳が作るランダムな値に変えたので、SHA-256 にした（auth.md 4）。PBKDF2 は管理者のパスワードだけに使う |
| SEC-5 | Cloudflare の DDoS 対策の範囲で守る。超えたら停止を受け入れる |
| LOG-6 / FUT-4 | 記録は SQL で絞り込める表として持つ。管理画面の Data Studio で読めて、SQL も実行できる（実測の結果 1） |
| NFR-2 | 起動の遅れがほぼない。校内の回線から届き、応答は1秒前後に収まる。ただし応答する拠点は日本ではなく米国だった（実測の結果 3） |
| NFR-3 | 無料枠は1日10万リクエスト。想定（予約20件/日、同時20人）の10倍でも十分収まる。5年分のデータ量は別の設計文書で見積もる |
| NFR-4 | GitHub Actions でテストを実行し、通ったときだけ wrangler でデプロイする |
| FUT-1 | 停止中の表示は、静的ファイルの側で API のエラーを検知して出せる（停止中でも静的ファイルは配れるかは、公開前に確かめる） |
| FUT-2 | 使用量は Cloudflare の GraphQL Analytics API で取れる。警告の仕組みは公開前に作る |
| FUT-3 | Cron Triggers は無料プランで使え、使われない間も動く。DO には過去30日に戻せる機能もある。※ 2026-11-17 追記：この機能は同じ DO の中のもので、アカウントや DO ごと失われたら戻せない。無料プランで使えるかも未確認。DO の外に置く控えの置き場所は決まっていない（R2 は不採用、KV は1件25MBまで、D1 は1つ500MBまで）。公開前に決める課題として残す（開発者が確認） |
| FUT-6 / FUT-7 | サーバ側の判定で、書き込める人を分ければよい。基盤の制約はない |
| FUT-8 | R2 は支払い方法の登録を求められる可能性があり、PRE-2 の「超えたら止まる」を保証できないので使わない。縮小した画像を D1 か KV に保存する（1件あたりの大きさに制約がつく） |

## 不採用にした案

| 案 | 理由 |
| --- | --- |
| Supabase（Postgres + Edge Functions） | 無料版は DB の活動が1週間ないと停止し、再開は手動。NFR-5 を満たすには外部の定期アクセス（GitHub Actions など）に頼るしかなく、それが壊れると黙って止まる。GitHub が運用の基盤に入り、PRE-11 の対象が増える。無料版には控えのダウンロードがない（FUT-3）。排他制約（`EXCLUDE`）で重複を防げる点は優れている |
| Google Apps Script + スプレッドシート | 接続元の IP が取れず、SEC-3 の「同じ相手からの試行の制限」が作れない。応答が1〜数秒かかり、NFR-2 を満たしにくい。CI からのデプロイに Google アカウントの認証情報が要る（NFR-4） |
| Firebase | サーバ側の処理（Cloud Functions）に従量課金の Blaze プランが要る（PRE-2） |
| Vercel / Netlify + 外部 DB | サービスが2つ以上に分かれ、PRE-11 で管理するアカウントが増える。Hobby プランは非商用の条件がある |

## 残るリスク

- **PBKDF2 の反復回数が推奨値に届かない。** workerd の PBKDF2 は10万回が上限で、推奨値（60万回）まで上げられない。管理者のパスワードの条件（SEC-3）を厳しくして補う（auth.md 4, 5）。
- **Worker の CPU 時間は1リクエスト10ms。** 台帳（DO）の中は1回の呼び出しで30秒なので、重い処理は台帳の中で行い、Worker 側ではしない（実測の結果 2）。
- **応答する拠点が日本ではない。** 無料プランでは、日本からの通信が米国の拠点に回された（実測の結果 3）。いまの速さで NFR-2 は満たせるが、拠点の割り当ては Cloudflare が決めるので、変わりうる。
- **上限を超えたら日本時間9時まで止まる。** その間は PRE-10 で運用する。
- **Durable Object は Cloudflare 専用。** 乗り換えるときは、予約台帳の部分の書き直しが要る。ルールの判定は DO に依存しない純粋な関数として分けておき、影響を小さくする。
- **校内のフィルタ。** いまは `*.workers.dev` に届くが、学校がフィルタを変えると使えなくなる（実測の結果 3）。
- **無料枠の数値は変わりうる。** 2026-11 時点の公式ページの値による。

## 追加するツール

| ツール | 理由 | 代わりの案 |
| --- | --- | --- |
| Node.js / npm | wrangler と Vitest を動かす | なし（Cloudflare の開発に必須） |
| wrangler | 手元での実行とデプロイ | 管理画面に手でアップロードする（NFR-4 の自動化ができない） |
| Vitest + `@cloudflare/vitest-plugin` | 本番と同じ実行環境で、DO を含めてテストする | Node 組み込みの `node:test`（DO を動かせない） |

`@cloudflare/vitest-plugin` は、もとは `@cloudflare/vitest-pool-workers` という名前だった。前の名前のほうは非推奨になり、更新が止まった。依存のパッケージ（`undici`・`zod`）に `npm audit` の指摘も残っていたので、2026-11-19 に新しい名前のほうへ移した（開発者が了承）。使い方（`cloudflareTest`、`cloudflare:test` の `runInDurableObject`）は変わらない。

## 実測の結果

2026-11-17〜18 に測った。使ったのは開発者の個人の Cloudflare アカウント（無料プラン、カードなし）で、そこに使い捨ての Worker（`spike/`。コミットしない）を置いた。本番は学校のアカウント（PRE-11）に作るので、測ったアカウントとは別になる。CPU 時間は `wrangler tail` の `cpuTime` で見た。

### 1. データの置き場所 → DO の SQLite にすべて置く

管理画面（Durable Objects → 名前空間 →「Data Studio」）で、DO の SQLite の表を読めて、SQL も実行できた。LOG-6 の確認ができるので、D1 は使わない。名前空間の画面には、使っている容量も出る。

1つの DO あたりの容量の上限は、管理画面に出ない。公式ページの記載は食い違ったまま（表は10GB、FAQ は無料プランで1GB）なので、1GB として扱う（logging.md 5）。

### 2. PBKDF2 の反復回数 → 100,000回

| 反復回数 | DO の中の CPU 時間（中央値 / 最大） | Worker の中（中央値 / 最大） |
| --- | --- | --- |
| 10,000 | 3 / 4 ms | 2 / 5 ms |
| 20,000 | 6 / 7 ms | 5 / 10 ms |
| 50,000 | 13 / 19 ms | 10 / 13 ms |
| 100,000 | 30 / 44 ms | 19 / 46 ms |

- 10万回を20回繰り返して CPU を約0.5秒使っても、DO・Worker のどちらでも止められなかった。公式ページでは、DO の CPU の上限は1回の呼び出しで30秒。Worker の無料プランは10msで、「たまに超えるのは許すが、超え続けると止める」とある。
- 台帳（DO）の中で計算する（auth.md 4）ので、10msの制限は効かない。反復回数は、workerd の上限の100,000回にする。ログイン1回の CPU は約30ms（最大44ms）。
- 採らなかった案（2026-11-18 に開発者が決定）
  - 10万回にして、パスワードの条件を緩める（12文字以上）：反復を上げた効き目をほとんど打ち消す。
  - 1万回のまま：回数を下げる理由だった「CPU 10ms」が、台帳の中では効かない。

### 3. 校内からの到達性と応答時間 → 届く

校内の回線の PC から測った（各20回、失敗は0回）。

| 測り方 | 中央値 | 最大 |
| --- | --- | --- |
| 毎回新しく接続する（`/ping`） | 0.457秒 | 1.102秒 |
| 接続を使い回す（`/ping`） | 0.135秒 | 0.437秒 |
| 接続を使い回す（DO に書く） | 0.168秒 | 0.469秒 |

- 応答した拠点は米国（`colo=LAX`・`SJC`・`SEA`）だった。接続元は日本（`loc=JP`）と判定されている。比べると、`www.cloudflare.com` には大阪（`KIX`）が応答した。それでも、NFR-2 の2〜3秒には十分な余裕がある。
- 手持ちのスマートフォンは、学校のルールで校内の回線に接続できないので、測っていない（NFR-2 の確かめ方は docs/progress.md）。

### 4. OPN-1 → 24時間

使われなかった時間を空けてから、最初の1回と、すぐ後の2回目を測った（校内の回線の PC から。2回目は、1回目で済ませた接続の準備を使い回す）。

| 使われなかった時間 | 1回目 | 2回目 |
| --- | --- | --- |
| 5分 | 0.730秒 | 0.194秒 |
| 10分 | 0.634秒 | 0.216秒 |
| 20分 | 0.833秒 | 0.198秒 |
| 40分 | 0.654秒 | 0.242秒 |
| 60分 | 0.646秒 | 0.187秒 |
| 約5時間（測り方が違う。curl で毎回新しく接続） | 0.705秒 | 0.46〜0.47秒 |
| 参考：温まった直後（5回） | 0.53〜0.81秒 | 0.17〜0.23秒 |

- 1回目は、使われなかった時間の長さによらず、温まった直後とほぼ同じだった。1回目と2回目の差は、端末の側で接続を準備する時間で、サーバの起動し直しによる遅れは測れるほど大きくなかった。どの場合も、例外を使わずに NFR-2 の2秒に収まる。
- それでも遅くなりうるのは、長くリクエストがなかった後の1回目で、台帳がたまった自動の変化（RSV-21）をまとめて反映するときになる。この重さは、使われなかった期間が長いほど大きい。
- そこで OPN-1 は **24時間** にする（2026-11-18 に開発者が決定）。例外が効くのを、遅くなる理由が実際にある場面（休み明けなど）に絞り、ふだんの利用はすべて2〜3秒の基準で測る。
- 採らなかった案：10分・1時間。確かめやすいが、実測では遅れが見えないのに基準を緩める理由を説明できない。
- たまった変化を反映する重さは、本物の台帳ができてから、長い休みの後を想定して測る（下の「まだ確かめていないこと」）。

### まだ確かめていないこと

- 1日の上限を超えて止まっている間も、静的ファイルが配られるか（FUT-1）。
- 長い休みの後の最初のリクエストで、たまった自動の変化をまとめて反映する重さ。本物の台帳ができてから測る。台帳の中なので、上限は30秒。
- FUT-3 の「過去30日に戻せる機能」が無料プランで使えるか。

`spike/` はリポジトリに含めていない。入口は `/ping`、`/pbkdf2?iter=N`、`/do`、`/do-pbkdf2` の4つ。ほかに、使われなかった時間を空けて測るスクリプト（`idle.js`）がある。
