## 決定

### 1. 自動テストの層

| 層 | 対象 | 書き方 | 主に確かめること |
| --- | --- | --- | --- |
| ルール | `src/rules/` | 関数に、データと時刻を渡して結果を見る。DB も DO も使わない | 予約のルール（RSV-2〜RSV-20）。要件の ID ごとに、受け付ける場合と断る場合（理由のコード）を書く |
| 部品 | `src/lib/` | 関数の入出力を見る | 学籍番号の正規化（USR-4）、名前・期生の検証（USR-5, USR-6）、時刻の換算と切り捨て（TIM-1〜TIM-4）、時刻の形（TIM-3） |
| 台帳 | `src/ledger.js` と `src/api/`、`src/store/` | `runInDurableObject` で台帳に入り、`handle(request, clock)` を任意の時刻を返す時計で呼ぶ。応答と、その後の表の中身を見る | 認証と証明の止まり方（USR-1, USR-2, ADM-2, ADM-3）、自動の変化の反映と順序（RSV-21, RSV-22）、同時の操作（RSV-23）、記録（LOG-1〜LOG-4）、応答に他人の学籍番号が入らないこと（VIW-2）、試行の制限（SEC-3）、途中で失敗したら何も書かれないこと |

- 数が最も多くなるのはルールの層。速く、時刻を自由に選べ、どのルールで断ったかをコードで確かめられる（RSV-27）。
- 台帳の層は、ルールの層で確かめたことを繰り返さない。つながり（認証→反映→判定→書き込み→記録）が正しいかを、代表的な操作で確かめる。
- 同時の操作（RSV-23）は、複数のリクエストを待たずに続けて送り（`Promise.all`）、すべての応答が返った後の表の中身が RSV-23 の挙げる条件に反しないことを確かめる。対象は、重なる確保（RSV-3）、件数の上限（RSV-4）、利用中の機器の削除（MNG-2）、最後の管理者の削除（ADM-2）、機器の名前と管理者の ID の重複（MNG-1, ADM-2）。どちらが通るかは決めず、「通るのは一方だけ」を確かめる。
- テストはそれぞれ空の台帳から始める（台帳の層のテストは、テストごとに `newUniqueId()` で新しい台帳を作る）。前のテストの結果に左右されない。

#### テストの名前

要件の ID を先頭に置き、受け付けるか断るかと、その条件を書く。

```js
describe('RSV-3 同じ機器で重なる予約は確保できない', () => {
  test('RSV-3 受け付ける：10:00 に終わる予約の後に 10:00 から確保する（TIM-2）', …)
  test('RSV-3 断る（RULE_OVERLAP）：既存の 10:00〜11:00 に 10:30〜11:30 を確保する', …)
})
```

ID で検索すれば、その要件のテストがすべて見つかる。

#### 自動テストにしないもの

| もの | 確かめ方 | 理由 |
| --- | --- | --- |
| 画面の動き | 手元の `wrangler dev` とテスト用の Worker で、手で操作して確かめる（下の 5） | 画面を動かすテストの道具（Playwright など）が増える。ルールの判定はサーバ側にあり（USR-1, RSV-24）、画面はそれを表示するだけ |
| 対応環境（NFR-1） | iOS の Safari、Android の Chrome、PC の Chrome と Edge で、手で確かめる | 実機でしか確かめられない |
| 性能（NFR-2） | 要件どおり、校内で手持ちのスマートフォンで各操作を10回測る | 要件が測り方を定めている |

画面の確認の手順（何をどの順に試すか）は、詳細設計で一覧にする。

### 2. 変更から反映までの流れ（NFR-4）

2026-11-20 に開発者が決めた。作業は `dev` ブランチで行い、`dev` はテスト用の Worker に、`main` は本番の Worker に反映する。

```
手元で変更 → npm test → dev にコミット → dev を push
                                            │
                          GitHub Actions ───┤ ① テスト
                                            │ ② dev への push で、①が通ったら
                                            ▼
                                   テスト用の Worker（手で確かめる）
                                            │
                     開発者が決めたときに dev を main にマージして push
                                            │
                          GitHub Actions ───┤ ① テスト
                                            │ ③ main への push で、①が通ったら
                                            ▼
                                       本番の Worker
```

| 仕組み | 内容 |
| --- | --- |
| テストのジョブ（`test`） | `npm ci` → `npm test`。どのブランチの push でも、プルリクエストでも動く |
| テスト用へのデプロイ（`deploy-test`） | `dev` への push のときだけ。`needs: test`。`npx wrangler deploy --env test` |
| 本番へのデプロイ（`deploy-production`） | `main` への push のときだけ。`needs: test`。`npx wrangler deploy` |
| 鍵 | Cloudflare の API トークン（Workers の編集だけを許すもの）とアカウント ID を、GitHub の Actions のシークレットに置く。2つのデプロイのジョブで同じものを使う。トークンは学校のアカウントが作る（PRE-11） |
| ワークフローの権限 | `permissions: contents: read`。GitHub への書き込みは要らないので、ワークフローの GitHub トークンを読み取りだけにする（2026-11-20 に開発者が了承） |
| デプロイの順番 | `concurrency`（ブランチごと、`cancel-in-progress: false`）で、同じブランチのデプロイを1つずつ順に行う。続けて push したとき、古い版が新しい版の後に反映されないように（2026-11-20 に開発者が了承） |

3つのジョブは1つのワークフロー（`.github/workflows/test.yml`）に置く。`needs: test` は同じワークフローの中のジョブにしか効かないため。

- **ブランチの使い方。** コミットと push は `dev` に行う。`main` には直接コミットしない。`dev` を `main` にマージするのは、開発者が指示したときだけ。テストを通らない変更は、どちらの Worker にも反映されない（NFR-4）。本番に出るのは、テスト用の Worker で確かめた `dev` の内容だけになる。
- **v0.1.0 は本番にデプロイしない**（2026-11-20 に開発者が決定）。本番へのデプロイのジョブは作っておくが、v0.1.0 の間は `dev` を `main` にマージしない。`main` は 2026-11-20 の時点（cff201b）のまま残す。
- **手元からデプロイしない。** 手元の `wrangler deploy` はテストを通らずに反映できてしまう（NFR-4）。デプロイは GitHub Actions だけで行う決まりにする。決まりを守りやすいよう、`package.json` にはデプロイのコマンドを置かない。
- **反映を止めたいとき。** 稼働中のシステムに問題が出たら、Cloudflare の管理画面か `wrangler rollback` で前の版に戻せる。戻した後の直しも、同じ流れで行う。
- **GitHub が使えないとき。** デプロイができなくなるだけで、稼働中のシステムは止まらない（platform-selection.md）。

`wrangler-action`（Cloudflare が配る GitHub Actions の部品）は使わず、`npx wrangler deploy` を直接呼ぶ。使う道具が1つ減り、手元で打つコマンドと同じなので読みやすい（PRE-5）。

### 3. 版をそろえる

| もの | そろえ方 | 理由 |
| --- | --- | --- |
| Node.js | `.nvmrc` と `package.json` の `engines` に版を書き、GitHub Actions もそれを使う | 手元と CI で結果が変わらないように |
| npm のパッケージ | `package-lock.json` をコミットし、CI は `npm ci` で入れる | 同上 |
| Workers の動き | `wrangler.jsonc` の `compatibility_date` を固定する | 基盤の更新で動きが変わらないように。上げるときはテストを通してから |

### 4. 台帳の表の変更

- **最初のデプロイ。** `wrangler.jsonc` の `migrations` に、台帳のクラスを SQLite を使う DO として登録する（`new_sqlite_classes`）。
- **表の変更。** architecture.md 7 のとおり、台帳がスキーマの版を持ち、起動したときに足りない変更を順に適用する。変更は「列や表を足す」形にし、既存の列を消したり意味を変えたりしない（LOG-5、FUT の受け入れ）。
- **前の版に戻したとき。** 新しい表・列があっても古いコードが動くよう、上の「足す形」を守る。

表の変更を適用する手順そのものもテストする（空の台帳から最新の版まで、と、1つ前の版から最新の版まで）。

### 5. 環境

| 環境 | Worker の名前 | 反映するもの | 使い方 |
| --- | --- | --- | --- |
| 手元（`wrangler dev`） | — | 手元のコード | 開発と、実装の途中の画面の確認。台帳は手元に作られる |
| テスト用 | `dxplace-reservation-system-test`（`*.workers.dev`） | `dev` | 開発者の手での確認（結合テスト、対応環境、性能）。テストのデータはここに置き、本番の台帳に残さない（LOG-2、LOG-5） |
| 本番 | `dxplace-reservation-system`（`*.workers.dev`） | `main` | 稼働中のシステム。v0.1.0 では作らない（上の 2） |

- **置き場所。** 2つとも学校のアカウント（PRE-11）に置く（2026-11-20 に開発者が決定）。API トークンは1つで済む。
- **設定の分け方。** `wrangler.jsonc` の環境 `env.test` で分ける。名前は wrangler が `（上の名前）-test` を付ける。`durable_objects` と `migrations` は環境に引き継がれないので、`env.test` の中に同じものを書く。`main`・`assets`・`compatibility_date` は上の値を引き継ぐ。
- **台帳は Worker ごとに別。** DO は Worker ごとに作られるので、テスト用と本番のデータは混ざらない。テスト用の台帳を空に戻す手順は v0.1.0 では作らない（最初のデプロイでは空なので、結合テストの段 1 から始められる）。要るようになったら決める。
- **`MAINT_KEY`。** Worker ごとにシークレットとして置き、値は別にする（api.md 6.2 の 1 の手順で作る）。テスト用の値が漏れても本番に響かない。設定は管理画面か `npx wrangler secret put MAINT_KEY --env test`（本番は `--env` なし）で行い、ふだんは消しておく（auth.md 6）。GitHub のシークレットには置かない（デプロイのジョブは使わない）。

### 6. 費用（PRE-2）

- GitHub Actions は、公開のリポジトリなら無料。非公開でも、無料の範囲（月2,000分）に対して、テストとデプロイは1回数分で、十分に収まる。リポジトリを公開にするかどうかは、費用には関係しない。
- GitHub にも支払い方法を登録しない。範囲を超えたら止まるだけになる。
- **Cloudflare の無料の範囲は、2つの Worker で分け合う。** 1日の上限（Workers と DO のリクエスト10万回、DO の稼働時間 13,000 GB-s）と保存の 5 GB は、アカウント全体で数える。テスト用の Worker は開発者の手での確認にしか使わず、1回の確認で数百回ほどなので、受け入れる。カードを登録しないので、超えても費用は出ず止まるだけになる（PRE-2）。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 画面も自動テストにする（Playwright など） | 道具が増える。ルールはサーバ側で確かめている |
| テストをルールの層だけにする | 自動の変化の反映や記録、証明の止まり方は、台帳を通さないと確かめられない |
| 手元からのデプロイも認める | テストを通らない変更が反映されうる（NFR-4） |
| `wrangler-action` を使う | 道具が1つ増える。`npx wrangler deploy` で足りる |
| 確認用の環境を作らず、本番で確かめる（2026-11-16 の案） | 本番の台帳にテストのデータが残る（LOG-2、LOG-5 で消せない）。2026-11-20 にテスト用の Worker を作る形に変えた |
| `main` だけを使い、本番へのデプロイを手動（`workflow_dispatch`）やタグの push で行う | 開発者が `dev` と `main` を分ける形を選んだ（2026-11-20）。どのブランチの内容がどこにあるかが名前でわかる |
| テスト用の設定を別のファイル（`wrangler -c wrangler.test.jsonc`）にする | 同じ値を2つのファイルに書くことになり、ずれやすい |
| Cloudflare のプレビュー URL（版のアップロード）で確かめる | 本番と同じ DO につながり、データが分かれない |
| テスト用の Worker を開発者の個人のアカウントに置く | 無料の範囲は分かれるが、PRE-11 から外れ、トークンが2つ要り、引き継ぎで失われうる |
| 表の変更を wrangler の機能で行う | DO の SQLite の表は、DO の中のコードで作り変える仕組みになっている |

## 残るリスク

- **手元からのデプロイは決まりで止めているだけ。** Cloudflare のアカウントの権限を持つ人は、手元から `wrangler deploy` できてしまう。権限の分け方で防ぐかは、学校のアカウントができてから決める。
- **テスト用の Worker を使い切ると本番も止まる。** 無料の範囲をアカウントで分け合うため（上の 6）。テスト用の Worker の URL は確認する人にだけ伝える。
- **`main` への push はそのまま本番に出る。** テストが通れば止める仕組みはない。`main` には直接コミットせず、マージは開発者の指示のときだけ行う決まりで防ぐ。
- **画面の誤りは自動では見つからない。** 画面の確認の手順を詳細設計で一覧にし、変更のたびに手で確かめる。

## 要件の読み方（確認済み）

- **画面を自動テストの対象にしない（NFR-4）。** NFR-4 が自動テストで確かめることを求めているのはルール。画面は手で確かめる（2026-11-16 に開発者が確認）。
