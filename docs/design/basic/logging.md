# 記録の持ち方

- 状態：決定
- 日付：2026-11-16
- 関係する要件：LOG-1〜LOG-6, USR-7, SEC-3, SEC-4, SEC-5, PRE-2, NFR-3, FUT-4
- 前提：[domain-model.md](domain-model.md) 5（記録のまとまり）、[auth.md](auth.md) 7（失敗を数える表が失敗の記録を兼ねる）、[platform-selection.md](platform-selection.md)（DO の SQLite に置く。管理画面から SQL で見られる。実測の結果 1）

## 決定

### 1. 表は2つに分ける

| 表 | 中身 | 消すか |
| --- | --- | --- |
| 出来事の記録 | 失敗の記録を除く、記録の対象のすべて（下の 2） | 消さない（LOG-5） |
| 認証の失敗 | 共有された情報による利用の開始・管理者の認証・保守用の API の失敗を、相手と10分の区切りごとに1行にまとめたもの（下の 4） | 上限を超えたら古いものから消す（LOG-4 の例外） |

分ける理由：認証の失敗は外部の者が好きなだけ起こせるので、消してもよい（LOG-4）。消してはいけない記録と同じ表に入れると、消す処理が誤って消してはいけない記録に及ぶおそれがある。

### 2. 出来事の記録

1件に次の項目を持つ。

| 項目 | 内容 |
| --- | --- |
| 時刻 | 実際の時刻（TIM-5）。自動の変化はルール上の時刻（RSV-21） |
| だれが | 種類（利用者・管理者・自動・保守用の API）と、利用者または管理者の番号 |
| 何を | 出来事の種類（下の表） |
| 何に | 予約・機器・利用者・管理者の番号のうち、関係するもの |
| 詳しく | 変化の前後の値、原因など（JSON の文字列） |

「何に」の機器と利用者の番号は、関係するものがあれば必ず入れ、索引を付ける。予約の出来事なら、その予約の機器と利用者を入れる。これで機器・利用者・期間で絞り込める（FUT-4）。

#### 出来事の種類

| 種類 | 要件 | 「詳しく」に入れるもの |
| --- | --- | --- |
| 予約の確保、予約なしの利用 | LOG-3 | 開始・終了時刻 |
| 予約の状態の変化（利用開始、取消、無断不使用、終了、管理者による取消、管理者による終了） | LOG-3 | 前後の状態、原因（管理者による取消・終了）、書き換えた時刻（RSV-15 の前倒しの開始時刻、RSV-18・MNG-3 の終了時刻） |
| 予約の時間帯の変更（RSV-9, RSV-10） | LOG-3 | 前後の開始・終了時刻 |
| 利用者を作った、名前・期生を置き換えた | USR-7, LOG-1 | 前後の名前・期生 |
| 機器の追加・名前の変更・削除 | LOG-4, LOG-2 | 前後の名前 |
| 数値の変更 | LOG-4 | 項目、前後の値、有効になる時刻 |
| 管理者のアカウントの作成・削除・パスワードの設定し直し | LOG-4, LOG-2 | 対象の ID と表示用の名前。パスワードは入れない |
| 共有された情報の設定・変更 | LOG-4 | 新しい版の番号。値もハッシュも入れない |
| 管理者の認証の成功、認証を解いた | LOG-4 | 接続元の IP |

- 「終了」が本人の操作によるか自動によるかは、「だれが」で区別する（domain-model.md 4.1）。
- 状態の変化に伴って時刻を書き換えたとき（RSV-15 の前倒し、RSV-18・MNG-3 の終了）は、状態の変化の1件に書き換えた時刻の前後を入れ、時間帯の変更の記録を別に書かない。1回の操作を1件にし、時刻の書き換えをどの状態の変化でも同じ形で持つため（2026-11-19 に開発者が決定。採らなかった案：前倒しを時間帯の変更として別の1件に書く。LOG-3 の「時間帯の変更（RSV-15 を含む）」を種類だけで引けるが、1回の操作が2件になり、終了の書き換えと形が揃わない）。LOG-3 の時間帯の変更は、時間帯の変更の記録と、開始時刻の前後を持つ状態の変化の記録を合わせて引く。
- 保守用の API による操作は LOG-4 の対象ではないが、「だれが」を保守用の API として記録する（auth.md 6）。
- 共有された情報による利用の開始の成功は記録しない（LOG-4 の対象は管理者の認証）。証明の表に作った時刻が残る。
- 読むだけのリクエストは記録しない。そのリクエストで反映した自動の変化は記録する。

記録は、その変化を書き込むのと同じトランザクションで書く（time-and-concurrency.md 4）。変化だけが残って記録が欠けることがない。

### 3. 記録に書かないもの（SEC-4）

- 管理者のパスワード、共有された情報の値、それらのハッシュ
- 証明（Cookie）の値と、そのハッシュ
- 保守用の鍵

記録を書く関数（`src/store/` の中の1つ）は、「詳しく」に入れる項目を種類ごとに決めた形でだけ受け取る。リクエストの本文をそのまま記録に入れない。

### 4. 認証の失敗の記録（LOG-4「方法は設計で定める」）

auth.md 7 の、失敗を数える表を兼ねる。1行が「入口・相手・10分の区切り」の組で、次を持つ。

| 項目 | 内容 |
| --- | --- |
| 入口 | 共有された情報、管理者の認証、保守用の API |
| 相手 | 接続元の IP（IPv6 は先頭64ビット） |
| 区切りの始まり | 時刻を10分で切り捨てたもの |
| 失敗の回数 | 上限（auth.md 7）まで |
| 最初と最後の失敗の時刻 | 実際の時刻 |
| 管理者の ID | 管理者の認証のとき、最後に試された ID（形式に合わないものは「形式外」）。ID がない場合とパスワードが違う場合の回数を分けて持つ |

- **上限に達した後の試行は書き込まない。** 断るだけにする。1つの相手が書ける行と回数に上限ができ、外部からの試行で書き込みの上限（下の 5）を使い切られにくい。
- **行の数に上限を置く。** 全体で10,000行を超えたら、区切りの始まりが古いものから消す。1行は100バイト程度なので、上限まで増えても約1MB。
- **まとめた結果、わからなくなること。** 個々の試行の時刻と、上限を超えた後に何回試されたか。追跡には、相手・時刻の範囲・回数があれば足りると考える。

### 5. 無料プランの範囲に収まるか（PRE-2, NFR-3）

#### 無料プランの上限（2026-11-13 更新の公式ページによる）

| 項目 | 上限 | 超えたら |
| --- | --- | --- |
| 保存容量 | アカウント全体で5GB。1つの DO あたりは、公式ページの中で1GBと10GBの記載が食い違っている（管理画面にも上限は出ない）。小さいほうの1GBとして見積もる | 書き込みが失敗する（読むことはできる） |
| 書き込んだ行 | 1日10万行（日本時間9時にリセット） | その日の書き込みが失敗する |
| 読んだ行 | 1日500万行 | その日の読み取りが失敗する |
| DO へのリクエスト | 1日10万回 | その日のリクエストが失敗する |
| DO の稼働時間 | 1日 13,000 GB-s | 同上 |

#### 保存容量（5年分）

1件の大きさを、予約は150バイト、出来事の記録は250バイト（索引を含めて）と見る。予約1件あたりの出来事は、確保・状態の変化・時間帯の変更で3〜5件とみる。

| | 想定の規模 | 10倍 |
| --- | --- | --- |
| 予約 | 3.7万件 × 150B ≒ 6MB | 37万件 ≒ 55MB |
| 出来事の記録 | 18万件 × 250B ≒ 45MB | 180万件 ≒ 450MB |
| 認証の失敗 | 最大 1MB | 最大 1MB |
| 合計 | 約50MB | 約510MB |

このほかの表（利用者、機器、管理者、数値の設定、証明）は小さい。証明（auth.md 3）は、有効な証明を持つ端末には作り直さない（auth.md 2）ので、端末の数 × 共有された情報の変更の回数ほどの行で、数MBに満たない。

想定の規模は1GBに十分収まる（NFR-3 の「必ず収まる」）。10倍でも収まる見込みだが、余裕は2倍程度。「詳しく」には必要な項目だけを入れ、長くしない。

#### 1日の書き込み

予約1件の確保から終了までで、予約の行と出来事の行を合わせて10行程度（索引の更新を含めて多めに見る）。想定の規模で1日200行、10倍で2,000行で、10万行に遠く及ばない。

外部からの試行で書き込めるのは、1つの相手につき10分ごとに上限の回数まで（上の 4）。10万行を使い切るには、数千の相手から試し続ける必要がある。それが起きたらその日は止まる。SEC-5 で許容している。

#### 1日の読み取り

読んだ行は、SQL が調べた行の数で数えられる。索引のない列で記録の表を絞り込むと、表全体を調べることになり、すぐに上限に近づく。そこで、ふだんの処理（予約状況・自分の予約・自動の変化の反映）では記録の表を読まない。予約の表を引くときは、機器・状態・時刻の索引を使う。索引の定義は詳細設計で決める。

### 6. 記録の確認（LOG-6, FUT-4）

v0.1.0 では確認の画面を作らない（LOG-6）。基盤の管理機能から SQL で確認する前提にする。たとえば機器3の、日本時間 2026-11-21 の1日分なら、次のようになる（表と列の名前は詳細設計で決める）。

```sql
SELECT datetime(at / 1000, 'unixepoch', '+9 hours') AS 時刻, kind, detail
FROM events
WHERE device_id = 3 AND at >= 1795186800000 AND at < 1795273200000
ORDER BY at;
```

管理画面の Durable Objects → 名前空間 →「Data Studio」で、表を読めて、SQL も実行できる（platform-selection.md 実測の結果 1）。上の SQL もそこで実行する。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 認証の失敗も、出来事の記録と同じ表に1件ずつ書く | 外部の者が好きなだけ増やせる。消すときに、消してはいけない記録に及ぶおそれがある |
| 上限を超えた後の試行も回数として書き込む | 試行のたびに書き込みが起き、1日の書き込みの上限を使い切られやすい |
| 「詳しく」も列に分ける | 種類ごとに要る項目が違い、列が増えて空の列が多くなる。絞り込みに使う機器・利用者・時刻だけを列にすれば FUT-4 に足りる |
| 記録を Workers のログ（`console.log`）に出す | 保存期間が短く、絞り込みも限られる。消さない（LOG-5）を満たせない |

## 要件の読み方（確認済み）

- **上限に達した後の試行を書かないこと（LOG-4）。** LOG-4 が認める「まとめる」の範囲とする。上限後に何回試されたかはわからなくなる（2026-11-17 に開発者が確認）。

- **10倍の規模での容量（NFR-3）。** 5年分で1GBに対して余裕が2倍程度だが、NFR-3 では10倍は「目標」なので、この見積もりで足りるとする。1つの DO あたりの実際の上限は、管理画面にも出なかった（platform-selection.md 実測の結果 1）。1GB として扱う（2026-11-16 に開発者が確認）。
