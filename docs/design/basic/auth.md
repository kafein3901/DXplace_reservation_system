## 決定

### 1. 入口と API の分け方

| 種類 | 呼べる条件 | 例 |
| --- | --- | --- |
| 誰でも | なし | 共有された情報による利用の開始（USR-2）、管理者の認証（ADM-2） |
| 利用者 | 利用を始めた証明が、現在の共有された情報に対して有効 | 空きの確認、予約の操作 |
| 管理者 | 管理者の認証した状態が有効 | 機器・数値・アカウント・共有された情報の管理 |
| 保守 | 保守用の鍵（下の 6） | 学校のアカウントによる管理者の作成・パスワードの設定し直し |

- 管理者の API は利用を始めた証明を求めない（ADM-2「USR-2 を前提としない」）。利用者の API は管理者の認証を受け付けない（ADM-1。管理者も予約は一般の利用者として行う）。
- 利用者として誰か（USR-3）は認証ではない（PRE-1）。渡し方は screens-and-api.md で決める。

### 2. 共有された情報は QR コードで渡す

共有された情報は、人が考えて打つ値ではなく、台帳が作るランダムな値にし、QR コードで校内に示す。手で入力する方法は設けない（2026-11-16 に開発者が決定）。

#### 設定・変更（ADM-3）

1. 管理者が管理者の画面で設定・変更の操作をする。値は入力しない。
2. 台帳がランダムな32バイトを作り、base64url（43文字）にする。台帳はそのハッシュ（下の 4）だけを保存し、共有された情報の版を新しくする。
3. 値は、この操作の応答で1回だけ管理者の画面に返す。画面は、利用者の画面の URL の後ろに `#k=値` を付けた URL を作り、QR コードとして表示する。管理者はこれを印刷して掲示する。
4. 画面を閉じると、値はもうどこからも取り出せない（SEC-4。ADM-3「わからなくなったら設定し直す」）。

そのため、QR コードを作り直すことは、必ず共有された情報の変更（ADM-3）になる。版が変わるので、それまでに利用を始めていた端末はすべて止まる（下の 3）。同じ値の QR コードを作り直す方法はない。掲示を増やしたいときは、表示したときに必要な枚数を印刷するか、画像を保存しておく。管理者の認証は止まらない（ADM-3）。

#### 利用の開始（USR-2）

1. 利用者がスマートフォンの標準のカメラで QR コードを読むと、利用者の画面が開く。
2. 画面の JavaScript が `#` の後ろの値を読み、台帳に送る。送ったら、すぐに `history.replaceState` で URL から `#` 以降を消す。
3. 台帳が値を確かめ、正しければ利用を始めた証明（下の 3）を渡す。

理由：

- **URL の `#` の後ろに入れる。** `#` 以降はブラウザがサーバに送らないので、基盤のアクセスの記録に値が残らない（SEC-4）。`?k=値` にすると記録に残る。
- **標準のカメラで読む。** 利用者の画面にカメラで読み取る機能を入れると、読み取りのライブラリが要る（iOS の Safari には標準の読み取り API がない）。URL なら、画面はふつうのページのままでよい。
- **ランダムな値にする。** 人が打たないので、長くランダムにできる。2^256 通りあるので、相手を変えながらの試行でも、ハッシュを持ち出された後でも、総当たりで当たらない（SEC-3）。人が考える値より強い。

制約（承知のうえ）：

- カメラのない PC（NFR-1 の PC の Chrome・Edge）では、そのままでは利用を始められない。スマートフォンで読んだ URL を自分の PC に送るなどして開けば始められる（下の「要件の読み方」）。
- 読んだ URL がカメラのアプリの履歴などに残りうる。印刷した QR コードと同じく、校内で共有される値として扱う。

#### 追加するライブラリ

| ライブラリ | 理由 | 代わりの案 |
| --- | --- | --- |
| qrcode-generator（MIT ライセンス。管理者の画面だけで使う） | ブラウザには QR コードを描く標準の機能がない。値は設定の操作のときにしか手に入らない（SEC-4）ので、その場で管理者の画面で描く必要がある | 管理者が外の道具で作る（外部のサイトで作ると値が外に渡る）。自分で QR コードの生成を書く（誤り訂正の計算などが長く、PRE-5 の点で読みにくい） |

ビルドは使わないので、配布されているファイルを版を固定して `public/js/vendor/` に置く（architecture.md 5）。

### 3. 証明（利用を始めた証明・管理者の認証した状態）の持ち方

どちらも同じ形にする。

1. 認証に成功したら、台帳がランダムな値（32バイト）を作り、Cookie で端末に渡す。
2. 台帳は、その値の SHA-256 だけを「証明」の表に持つ。値そのものは持たない。
3. リクエストのたびに、Cookie の値の SHA-256 を求め、表で引いて有効かを確かめる。

| 証明 | 表に持つもの | 有効の条件 | 止める操作 |
| --- | --- | --- | --- |
| 利用を始めた証明 | 値のハッシュ、どの共有された情報（の版）で始めたか、作った時刻 | 始めた版が現在の版と同じ | 共有された情報の設定・変更（ADM-3）で版が変わると、すべて無効 |
| 管理者の認証 | 値のハッシュ、管理者、パスワードの版、作った時刻、解いた時刻 | 管理者が削除されていない、パスワードの版が現在と同じ、解いていない | 認証を解く（その端末）、パスワードの設定し直し・削除（すべての端末。ADM-2） |

理由と補足：

- **表で確かめる。** 共有された情報の変更や管理者の削除で、すでに渡した証明を「直ちに」止める（ADM-2, ADM-3）には、サーバ側で確かめられる必要がある。署名だけで確かめる方式（JWT など）は止められない。
- **版で止める。** 共有された情報とパスワードに版（変更のたびに変わる番号）を持ち、証明は作った時点の版を持つ。変更のときに証明を1件ずつ無効にしなくてよい。
- **値はハッシュで持つ。** 基盤の管理機能でデータを見た人が、その値で利用者や管理者になりすませないように。値は推測できない長さなので、速い SHA-256 で足りる。
- **ハッシュは手順 2 の前に求める。** SHA-256 も Web Crypto では `await` が要る。データを読む前に求めれば、割り込まれても結果は変わらない（time-and-concurrency.md 4）。新しく渡す証明の値とそのハッシュも、成功するかどうかにかかわらず手順 2 の前に作っておく。共有された情報として送られた値のハッシュも同じ。
- **期限は付けない。** 利用を始めた証明は、USR-2「ADM-3 で止められるまで再入力しなくてよい」による。管理者の認証は、要件に期限がなく、管理者は共用 PC で作業しない（2026-11-16 に開発者が確認）ため。どちらも、ブラウザが Cookie の期限を最長400日程度に切り詰めるので、使われるたびに期限を延ばして渡し直す。

#### Cookie の属性

| 属性 | 値 | 理由 |
| --- | --- | --- |
| 名前 | `__Host-dxp_user`、`__Host-dxp_admin` | `__Host-` を付けると、ブラウザが `Secure`・`Path=/`・`Domain` なしを強制する |
| `HttpOnly` | 付ける | 画面の JavaScript から読めないので、仮に SEC-1 が破られても持ち出されにくい |
| `Secure` | 付ける | SEC-2。手元の `http://localhost` でも主要なブラウザは受け付ける |
| `SameSite` | `Strict` | ほかのサイトから送られたリクエストに Cookie が付かない（CSRF の対策） |
| `Max-Age` | 400日（使うたびに延ばす） | 上のとおり |

CSRF の対策として、状態を変える API（`GET` 以外）では、`Origin` ヘッダが自分のサイトと一致することも確かめる。

### 4. 秘密の値の持ち方（SEC-4）

| 値 | 方式 | 理由 |
| --- | --- | --- |
| 共有された情報 | SHA-256 | 台帳が作る256ビットのランダムな値なので、速いハッシュでも総当たりできない。PBKDF2 を使わないので、CPU の上限（platform-selection.md）にも響かない |
| 管理者のパスワード | PBKDF2-HMAC-SHA256（Web Crypto）。ソルトは値ごとにランダムな16バイト | 人が考える値なので、総当たりを遅くする必要がある |

- **反復回数。** コードの設定値にし、ハッシュと一緒に保存する（後から変えても古いハッシュを確かめられる）。値は実測で決める（platform-selection.md 未決事項2）。それまでは仮に 10,000 回。推奨（60万回）より大きく下げる分は、パスワードの条件（下の 5）で補う。
- **比べ方。** `crypto.subtle.timingSafeEqual` で比べる（比べる時間から値を推測されないように）。
- **記録。** 値そのものも、ハッシュも記録に書かない（LOG-4）。

### 5. 値の条件（SEC-3）

| 値 | 条件 | 比べるときの扱い |
| --- | --- | --- |
| 共有された情報 | 台帳が作る（上の 2）。人は値を決めない | 入力どおりに比べる |
| 管理者のパスワード | 15文字以上128文字以下。半角の英数字と記号（空白を除く表示できる ASCII） | 入力どおりに比べる |
| 管理者の ID（ADM-2「形式は設計で定める」） | 3文字以上32文字以下。半角の英小文字・数字・ハイフン・アンダースコアで、先頭は英字 | 全角を半角に、英字を小文字にそろえてから比べる |

理由：

- **15文字。** NIST SP 800-63B（第4版）は、単独で使うパスワードの最小を15文字としている。
- **長さ以外の条件（記号を必ず含む、など）は付けない。** 推測されにくさへの効き目が小さく、覚えにくくなる。人が考えた値は推測されやすいので、管理者の画面では「ランダムに作った値を使う」ことを案内する。

### 6. 学校のアカウントによる管理者の作成と復旧（ADM-2）

保守用の API（`/api/maint/…`）を置き、管理者のアカウントの作成とパスワードの設定し直しだけをできるようにする。

- 呼ぶには保守用の鍵が要る。鍵は Worker のシークレット（`MAINT_KEY`）として、Cloudflare の管理画面か `wrangler secret put` で設定する。設定できるのは Cloudflare のアカウントの権限を持つ人だけ（PRE-11）。
- シークレットが設定されていない間、保守用の API はすべて断る。ふだんは消しておき、使うときだけ設定する運用にする。
- 鍵は32バイト以上のランダムな値とし、試行の制限（下の 7）も同じようにかける。
- この API による操作は LOG-4 の対象ではない（ADM-2）。追跡のため、「保守用の API による」ことは記録に残す（値は含めない）。

理由：システムの外から管理者を作るには、DB に直接書くか、特別な入口を置くかのどちらかになる。DB に直接書くには、管理画面でハッシュを手で作って入れる必要があり、学校の教員には難しく、誤りやすい。鍵を設定できるのが Cloudflare のアカウントの権限を持つ人だけなので、ADM-2 の「システムの外から」にあたるとみなす（2026-11-16 に開発者が確認）。

### 7. 試行の制限（SEC-3）

| 入口 | 数えるもの | 上限 | 上限を超えたら |
| --- | --- | --- | --- |
| 共有された情報による利用の開始 | 同じ相手からの失敗 | 10分ごとに20回 | その10分の区切りが終わるまで、確かめずに断る |
| 管理者の認証 | 同じ相手からの失敗 | 10分ごとに10回 | 同上 |
| 保守用の API | 同じ相手からの失敗 | 10分ごとに5回 | 同上 |

- **同じ相手。** 接続元の IP アドレス（`CF-Connecting-IP`）。IPv6 は先頭64ビットでまとめる（1つの回線に多数のアドレスが割り当てられるため）。
- **失敗だけを数える。** 校内の回線では多くの利用者が同じ相手に見える（SEC-3）。成功も数えると、共有された情報の変更の直後に大勢が読み直したとき、正規の利用者が止められる。
- **数を確かめてからハッシュを計算する。** 上限を超えた相手には PBKDF2 を計算しないので、CPU の上限を使い切られにくい。管理者の認証は処理全体が `blockConcurrencyWhile` の中なので、同時に届いた試行が上限をすり抜けることもない。共有された情報の確認は `await` なしで行える（ハッシュは手順 2 の前に求める）ので、同じく割り込まれない。
- **アカウントごとの締め出しはしない。** 管理者 ID ごとに止めると、外部の者がわざと失敗して管理者を締め出せるため。相手を変えながらの試行には、値の条件（5）で耐える。
- **上限の根拠。** 共有された情報：QR コードなら打ち間違いはなく、失敗は主に変更前の古い QR コードを読んだときに起きる。変更の直後に学級の数人が古いものを読んでも20回には届かない。値はランダムなので、上限は総当たりの対策というより SEC-3 を形の上でも満たすためのもの。管理者の認証は入力する人が少ないので半分にした。

10分の区切りは、時刻を10分で切り捨てたもの（固定の区切り）にする。区切りの境目をまたぐと最大で2倍まで試せるが、影響は小さく、仕組みが単純になる。

失敗を数える表は、LOG-4 の「失敗の記録」を兼ねる。容量を使い切られない持ち方は logging.md で決める。

### 8. 応答

- 断るときは、ほかの操作と同じく理由のコードを返す（RSV-27）。たとえば、共有された情報が未設定、共有された情報が違う（古い QR コードなど）、試行の上限、証明が無効（変更で止められた）、管理者の ID かパスワードが違う、など。体系は screens-and-api.md で決める。
- 管理者の認証の失敗では、「ID がない」と「パスワードが違う」を区別して返さない（ID の有無を外から確かめられないように）。記録では区別する。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 共有された情報を人が決めて、手で入力する | 打ちやすい値は推測されやすく、長い値は打ち間違いが増える。開発者が QR コードを選んだ |
| QR コードと手での入力の両方を設ける | 手で打てる長さ・文字に値を制限することになる。開発者が QR コードだけを選んだ |
| QR コードに値だけを入れ、利用者の画面にカメラで読む機能を置く | 読み取りのライブラリが要る（iOS の Safari に標準の API がない） |
| 値を URL の `?` の後ろに入れる | 基盤のアクセスの記録に値が残る |
| 証明を署名付きの値（JWT など）にし、表に持たない | 直ちに止めることができない（ADM-2, ADM-3）。署名の鍵というシークレットが増える |
| 証明の値をそのまま表に持つ | 基盤の管理機能で見た人がなりすませる |
| 利用を始めた証明を `localStorage` に持つ | JavaScript から読めるので、SEC-1 が破られたときに持ち出される |
| 管理者の認証に期限を付ける | 要件にない。管理者は共用 PC で作業しないので、消し忘れの心配が小さい |
| 管理者 ID ごとに試行を止める（ロックアウト） | 外部の者が管理者を締め出せる |
| 成功も含めて試行を数える | 校内の回線で正規の利用者が止められる（SEC-3） |
| 学校のアカウントが DB に直接書いて管理者を作る | ハッシュを手で作る必要があり、難しく誤りやすい |

## 残るリスク

- **QR コードの写真が外に出る。** 写真を見た人は校内関係者と同じく使えるようになる。手で打つ値が漏れるのと同じで、気づいたら ADM-3 で変更する。
- **管理者のパスワードの反復回数が少ない。** 持ち出された後の総当たりへの強さを長さに頼っている。人が考えた15文字（よくある言葉の組み合わせなど）は、ランダムな15文字より弱い。
- **校内の回線から失敗が続くと、校内の全員が止まる。** 校内の利用者は外から同じ相手に見えるので、校内の回線から上限まで失敗すると、その10分は校内の誰も利用を始められない。わざと行う者は PRE-8 で想定しない。
- **保守用の鍵を設定したまま忘れる。** 鍵が十分に長ければ破られないが、運用で消すことを手順に入れる（運用手順の文書化は v0.1.0 に含めない。10章）。

## 要件の読み方（確認済み）

- **カメラのない PC での利用の開始（NFR-1）。** QR コードだけにしたので、PC では「スマートフォンで読んだ URL を PC に送って開く」などの手間が要る。URL を開けば PC の Chrome・Edge でも利用を始められ、その後の機能はすべて使えるので、NFR-1 を満たすとみなす（2026-11-16 に開発者が確認）。
