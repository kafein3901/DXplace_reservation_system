# 画面と API

- 状態：決定
- 日付：2026-11-16（2026-11-20 に USR-3・USR-7 の修正に合わせて 1・2・4・5・7 と要件の読み方を直した）
- 関係する要件：USR-2〜USR-7, ADM-1〜ADM-3, RSV-5〜RSV-18, RSV-25, RSV-27, VIW-1〜VIW-3, MNG-1〜MNG-3, SEC-1, TIM-1, TIM-3, NFR-1
- 前提：[architecture.md](architecture.md)（画面はビルドしない静的ファイル。API はすべて台帳で処理）、[domain-model.md](domain-model.md)、[time-and-concurrency.md](time-and-concurrency.md)、[auth.md](auth.md)

ここでは、画面の一覧と遷移、API の一覧、利用者として誰かの渡し方、応答の形、理由のコードの体系を決める。画面ごとの項目と動き、API ごとの入出力の細部、理由のコードの一覧は詳細設計で決める。

## 決定

### 1. 画面の作り：HTML は2つ、中は JavaScript で切り替える

| ファイル | 中の画面（JavaScript で表示を切り替える） |
| --- | --- |
| `public/index.html`（利用者） | 利用の開始の案内、ログイン、登録、名前・期生の変更、機器の予約状況、確保・予約なしの利用、自分の予約 |
| `public/admin.html`（管理者） | 認証、機器、予約の管理、数値、管理者のアカウント、共有された情報 |

理由：利用者として誰か（USR-3）は「画面を開いている間だけ」JavaScript の変数に持つ（architecture.md 6）。画面ごとに HTML を分けてページを移ると、移るたびに変数が消え、入力し直しになる。`sessionStorage` に持てば移れるが、端末に保存しないという USR-3 に反する。

画面の切り替えでは URL を変えない（機器を特定して直接開く機能は v0.1.0 に含めない。10章）。

### 2. 利用者の画面の遷移

```
QR コードを読む（#k=値 付きで開く）
   │
   ▼
[利用の開始]──失敗──▶ 理由を表示（古い QR コード、未設定、試行の上限）
   │ 成功（または証明が有効）
   ▼
[機器の予約状況]  機器を選ぶ・日を選ぶ・最新にする
   │                      ▲
   │ 予約する／使い始める  │
   ▼                      │
[ログイン]（未ログインのときだけ。ログイン済みならとばす）◀──▶ [登録]
   │ ログインか登録が成功
   ▼
[確保] または [予約なしの利用] ──▶ 結果を表示して予約状況へ戻る

[自分の予約]（どの画面からも開ける。未ログインならログインへ）
   取消・時間帯の変更・利用開始・利用終了

[名前・期生の変更]（どの画面からも開ける。未ログインならログインへ）
```

| 画面 | 内容 | 要件 |
| --- | --- | --- |
| 利用の開始 | `#k=` 付きで開かれたら値を送る。証明がなく `#k=` もなければ「QR コードを読んでください」と案内する | USR-2 |
| ログイン | 生徒か教員か、学籍番号。いつでも開き直して別の人に切り替えられる。登録の画面へ移れる | USR-3, USR-4 |
| 登録 | 生徒か教員か、学籍番号、名前、期生（生徒だけ）。成功したらその利用者でログインした状態になる。ログインの画面へ戻れる | USR-3〜USR-7 |
| 名前・期生の変更 | ログインしている利用者の名前、期生（生徒だけ）。ほかの利用者を選ぶ欄は置かない | USR-5〜USR-7 |
| 機器の予約状況 | 機器を1つ選び、日を選ぶと、その日の確保済みの時間帯・利用があった時間帯・空きを表示する。時間帯ごとに名前（生徒は期生も）と状態を出す。「最新にする」ボタンを置く | VIW-1〜VIW-3 |
| 確保 | 選んだ機器について、開始時刻と終了時刻を入れて確保する | RSV-5 |
| 予約なしの利用 | 選んだ機器が空いているとき、終了時刻を入れて使い始める | RSV-17 |
| 自分の予約 | 予約済・利用中の予約の一覧。それぞれに、取消・時間帯の変更・利用開始・利用終了のうち、いまの状態でできる操作を出す | RSV-7〜RSV-18 |

- 予約状況は、ログインの前でも見られる。見ることは「利用者として操作する」ことではないため（USR-3）。
- 操作の後は、そのつど表示を取り直す（VIW-3「操作した時点で最新」）。
- 全機器の空きの一覧は作らない（10章）。機器は選択肢から1つずつ選ぶ。機器の並びは作った順（機器の順番は10章）。

| --- | --- | --- |
| 認証 | ID とパスワード。認証を解くボタンは各画面に置く | ADM-2 |

| 数値 | 3つの数値の現在の値と変更 | RSV-25 |

| 共有された情報 | 設定・変更のボタン。押すと QR コードを表示する（auth.md 2） | ADM-3 |

### 4. 利用者として誰かの渡し方（USR-3, USR-7）

登録・ログイン・名前と期生の変更を、それぞれ別の API にし、その後の操作と分ける。

1. **登録**：画面は `POST /api/me/register` に「生徒か教員か・学籍番号・名前・期生」を送る。台帳は形式を確かめ（USR-4〜USR-6）、学籍番号を正規化し、利用者を引く。
   - いなければ作り、作ったことを記録する（USR-7, LOG-1）。
   - いれば断る（USR-3「すでにいる利用者は登録できない」）。名前・期生には触れない。理由のコードは詳細設計で決める。
2. **ログイン**：画面は `POST /api/me/login` に「生徒か教員か・学籍番号」（識別の組。USR-4）だけを送る。台帳は形式を確かめ、正規化し、利用者を引く。いなければ `NOT_FOUND_USER` で断る（USR-3「登録していない利用者はログインできない」）。何も書き込まず、記録もしない（下の理由）。
3. 登録とログインの応答には、正規化した学籍番号と利用者の内部の番号を入れる。画面はこれを変数に持ち、「ログインしている利用者」とする。ログインの応答に名前・期生を入れるかは詳細設計で決める（10章の「誰として操作しているかの表示」との関係を含む）。
4. **名前・期生の変更**：画面は `POST /api/me/change` に、ログインしている利用者の識別の組と、新しい名前・期生を送る。台帳は利用者を引き（いなければ `NOT_FOUND_USER`）、名前・期生がそれまでと異なれば置き換え、置き換えたことを記録する（USR-7, LOG-1）。同じなら何も書かない。
5. その後の操作では、画面は識別の組だけを送る。台帳はそれで利用者を引き、名前・期生には触れない。利用者がいなければ `NOT_FOUND_USER` で断る。

理由：

- USR-7 は、置き換えるのを登録と変更に限り、ログインを含むほかの操作では置き換えないとしている。名前・期生を受け取る API を登録と変更の2つだけにすれば、受け取らない API では置き換わりようがなく、そのことが API の形でわかる。
- 登録とログインを1つの API にまとめ、「名前があれば登録、なければログイン」と分けると、断る理由（すでにいる・いない）と記録の有無が中身の組み合わせで変わり、テストも画面の文も分かれにくい。
- ログインを記録しないのは、何も変えない操作だから。利用の開始の成功（auth.md、logging.md）と同じ扱いにする。誰が予約などを行ったかは、それぞれの操作の記録に残る（LOG-1）。
- 「自分の分だけを変更できる」（USR-7）は、変更の画面がログインしている利用者の識別の組だけを送り、ほかの利用者を選ぶ手段を持たないことで満たす。識別の組は認証ではない（PRE-1）ので、台帳はほかの利用者の組が送られたことを見分けない。これは USR-7 が承知のうえの制約としているもの。

- 識別の組は、利用者の操作の API の本文（JSON）に入れて送る。URL（`?` の後ろ）には入れない。学籍番号が基盤のアクセスの記録に残らないように（VIW-2 の趣旨）。
- 識別の組は認証ではない（PRE-1）。証明（Cookie）とは別に送る。
- 台帳は、利用者として誰かを端末ごとに覚えない。覚えると、開き直しても入力が残ることになり、USR-3 に反する。

### 5. API の一覧

すべて `/api/` の下に置き、JSON で受け渡す。利用者の識別を伴う API は、読むだけでも `POST` にする（本文に識別の組を入れるため）。

#### 誰でも呼べる

| API | 内容 | 要件 |
| --- | --- | --- |
| `GET /api/session` | 利用を始めているか（証明が有効か）を返す | USR-2 |
| `POST /api/session` | 共有された情報の値を受け取り、証明を渡す | USR-2 |
| `POST /api/admin/login` | 管理者の認証 | ADM-2 |

#### 利用者（証明が要る）

| API | 内容 | 要件 |
| --- | --- | --- |
| `POST /api/me/register` | 登録（上の 4） | USR-3〜USR-7 |
| `POST /api/me/login` | ログイン（上の 4） | USR-3, USR-4 |
| `POST /api/me/change` | 名前・期生の変更（上の 4） | USR-5〜USR-7 |
| `GET /api/devices` | 機器の一覧 | VIW-1 |
| `GET /api/devices/{id}/day?date=YYYY-MM-DD` | 指定した日の時間帯の一覧。時間帯ごとに、名前・期生・状態と、利用者の内部の番号を返す | VIW-1, VIW-2 |
| `POST /api/my/reservations` | 自分の予約済・利用中の一覧 | RSV-7 |
| `POST /api/reservations` | 確保 | RSV-2〜RSV-6 |
| `POST /api/walk-ins` | 予約なしの利用 | RSV-17 |
| `POST /api/reservations/{id}/cancel` | 取消 | RSV-8 |
| `POST /api/reservations/{id}/change` | 時間帯の変更 | RSV-9〜RSV-12 |
| `POST /api/reservations/{id}/begin` | 利用開始 | RSV-14, RSV-15 |
| `POST /api/reservations/{id}/finish` | 利用終了 | RSV-18 |

予約状況（`day`）は識別の組を受け取らない。見ることは「利用者として操作する」ことではなく、誰が見ても同じ応答になる。日は個人の情報ではないので URL に入れてよい。

予約状況の応答には、他の利用者の学籍番号を入れない（VIW-2）。代わりに利用者の内部の番号（domain-model.md 1 の連番）を入れる。内部の番号は操作の鍵ではない（操作は識別の組で行う）ので、知られてもその人として操作できない。登録とログインの応答にも自分の内部の番号を入れる。v0.1.0 の画面はこの番号を使わない。自分の予約を目立たせる表示は要件になく、公開までに足すとき（10章「誰として操作しているかの表示」と同じ時期）に、API を変えずに画面だけで見分けられるようにしておくためのもの（2026-11-17 に開発者が決定）。

#### 管理者（管理者の認証が要る）

| API | 内容 | 要件 |
| --- | --- | --- |
| `GET /api/admin/me`、`POST /api/admin/logout` | 認証の状態、認証を解く | ADM-2 |
| `GET /api/admin/devices`、`POST /api/admin/devices` | 機器の一覧、追加 | MNG-1 |
| `POST /api/admin/devices/{id}/rename`、`…/delete` | 名前の変更、削除 | MNG-1, MNG-2 |
| `GET /api/admin/devices/{id}/reservations` | 予約済・利用中の予約を、学籍番号を含めて一覧 | MNG-3 |
| `POST /api/admin/reservations/{id}/cancel`、`…/finish` | 管理者による取消・終了 | MNG-3 |
| `GET /api/admin/settings`、`POST /api/admin/settings` | 数値の確認、変更 | RSV-25 |
| `GET /api/admin/admins`、`POST /api/admin/admins` | 管理者の一覧、作成 | ADM-2 |
| `POST /api/admin/admins/{id}/delete`、`…/reset-password` | 削除、パスワードの設定し直し | ADM-2 |
| `POST /api/admin/shared-info` | 共有された情報の設定・変更（値を1回だけ返す） | ADM-3 |

#### 保守（保守用の鍵が要る）

| API | 内容 | 要件 |
| --- | --- | --- |
| `POST /api/maint/admins`、`POST /api/maint/admins/{id}/reset-password` | 管理者の作成、パスワードの設定し直し | ADM-2 |

保守用の API は画面を作らない。`curl` などで呼ぶ（手順は詳細設計で示す）。

#### 動詞を URL に入れる理由

`DELETE` や `PATCH` を使い分ける REST の書き方もあるが、ここでは「`GET` は読むだけ、それ以外は `POST` で、何をするかは URL の最後に書く」にそろえる。取消・利用開始のように、削除でも更新でもない操作が多く、URL を見ただけで何をするかがわかるため（PRE-5）。

### 6. 時刻の受け渡し

| もの | 形 | 例 |
| --- | --- | --- |
| 日（VIW-1） | `YYYY-MM-DD`（日本時間） | `2026-11-20` |
| 境界の時刻（開始・終了） | `YYYY-MM-DDTHH:mm`（日本時間。秒を持たない） | `2026-11-20T10:00` |

- 境界の時刻は、HTML の `<input type="datetime-local">` が返す形と同じ。秒を書けない形なので、分単位（TIM-3）が形の上で守られる。秒の付いた値や、形に合わない値は断る。
- 台帳は受け取ったら `src/lib/time.js` でミリ秒に直し、返すときに日本時間の文字列に戻す（time-and-concurrency.md 1）。
- 予約状況・利用者の機器の一覧・自分の予約の応答には、台帳の現在時刻（日本時間）も入れる（detailed/api.md 8.22・8.24・8.29）。画面は、時刻の入力の初期値などをこれから作り、端末の時計に頼らない（TIM-1）。

### 7. 応答の形と理由のコード（RSV-27）

成功：

```json
{ "ok": true, "data": { … } }
```

断るとき：

```json
{ "ok": false, "error": { "code": "RULE_OVERLAP" } }
```

- **コードは1つだけ返す。** 複数のルールに反するときは、詳細設計で決める確かめる順で、最初に反したものを返す。テストは、順が決まっていれば1つのコードで確かめられる。
- **画面に出す文は、画面の側でコードから作る**（`public/js/messages.js`）。台帳は文を返さない。文の言い回しを直すのに台帳を変えなくてよく、テストは文の変更に左右されない。知らないコードには、汎用の文を出す。
- **コードは種類ごとに頭をそろえる。** HTTP の状態コードもそれに合わせる。

| 頭 | 意味 | HTTP | 例 |
| --- | --- | --- | --- |
| `INPUT_` | 入力の形式が合わない | 400 | `INPUT_STUDENT_ID`（USR-4）、`INPUT_NAME`（USR-5）、`INPUT_TIME`（TIM-3） |
| `AUTH_` | 認証が要る、無効、違う | 401 | `AUTH_REQUIRED`、`AUTH_SHARED_INFO_WRONG`、`AUTH_SHARED_INFO_UNSET`（USR-2）、`AUTH_ADMIN_FAILED`（ADM-2） |
| `LIMIT_` | 試行の上限 | 429 | `LIMIT_ATTEMPTS`（SEC-3） |
| `NOT_FOUND_` | 指したものがない、自分のものでない | 404 | `NOT_FOUND_RESERVATION`、`NOT_FOUND_USER`（登録していない） |
| `STATE_` | いまの状態ではできない | 409 | `STATE_NOT_RESERVED`（RSV-8）、`STATE_NOT_IN_USE`（RSV-18） |
| `RULE_` | 予約のルールに反する | 409 | `RULE_OVERLAP`（RSV-3）、`RULE_COUNT`（RSV-4）、`RULE_LENGTH`（RSV-6）、`RULE_PAST`（TIM-6）、`RULE_DEVICE_IN_USE`（MNG-2）、`RULE_ADMIN_LAST`（ADM-2） |

- 自分のものでない予約を指したときは、`NOT_FOUND_RESERVATION` を返す（他人の予約があるかどうかを、操作で確かめられないように）。
- コードの一覧と、それぞれがどの要件の ID に当たるかは、詳細設計で表にする。テスト名にも要件の ID を入れる（CLAUDE.md）。
- **想定していない例外（バグ）は断る理由ではないので、コードを付けない。** HTTP 500 で `{ "ok": false }` だけを返す。画面は、JSON として読めない応答（基盤が止まったときなど。FUT-1）と同じく汎用の文を出す。2026-11-19 に詳細設計（detailed/error-codes.md）で足した。

### 8. 画面での表示の決まり

- 利用者が入力した文字列（名前、機器の名前など）は、`textContent` で入れる。`innerHTML` には入れない（SEC-1）。
- 時刻は `timeZone: 'Asia/Tokyo'` を指定して表示する（time-and-concurrency.md 1）。
- 画面での入力の検証は、打ち間違いを早く知らせるためだけに行う。台帳で必ず確かめ直す（USR-1, RSV-24）。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 画面ごとに HTML を分ける | ページを移ると利用者として誰か（USR-3）が消える |
| 利用者として誰かを `sessionStorage` に持つ | 端末に保存しないという USR-3 に反する |
| 操作のたびに名前・期生も送り、違えば置き換える | 入力していない操作で名前が書き換わる（USR-7） |
| 1つの API で、いなければ作り、いれば名前・期生を置き換える（2026-11-19 までの `POST /api/me`） | すでにいる利用者の登録を断れず（USR-3）、ログインにあたる操作で名前が置き換わる（USR-7） |
| 登録とログインを1つの API にし、名前の有無で分ける | 断る理由と記録の有無が中身の組み合わせで変わる（上の 4） |
| ログインでも名前・期生を送り、違えば置き換える | ログインでは置き換えない（USR-7） |
| 台帳が、端末の証明ごとに利用者として誰かを覚える | 開き直しても入力が残る（USR-3） |
| 識別の組を URL の `?` の後ろで送る | 学籍番号が基盤のアクセスの記録に残る |
| 予約状況に識別の組を送り、台帳が自分の予約に印を付ける | 要件にない機能。読むだけの API が `POST` になる |
| 予約状況で学籍番号と生徒か教員かを返し、別の API で名前に変換する | 応答に他の利用者の学籍番号が入る（VIW-2）。学籍番号はその人として操作する鍵になる |
| 予約状況で内部の番号だけを返し、別の API で名前に変換する | リクエストが増え（NFR-2）、画面でつなぎ合わせる処理が要る。名前はどのみち全員に見せる |
| 時刻をミリ秒の数値で受け渡す | 画面の入力（`datetime-local`）との変換が両側に要り、秒を含む値も送れてしまう |
| 台帳が画面に出す文を返す | 文を直すたびに台帳を変えることになり、テストも文に左右される |
| 反したルールをすべて返す | すべてを確かめるために判定を途中で止められず、判定が複雑になる。v0.1.0 では1つで足りる |

## 要件の読み方（確認済み）

- **名前を置き換える時点（USR-7）。** 置き換えるのは、名前・期生の変更の画面で決定したとき（`POST /api/me/change`）だけとする。登録はすでにいる利用者を断る（USR-3）ので、登録で置き換えることはない（USR-7 の「登録・変更のほか」の登録は、名前・期生を初めて持たせることと読む）。ログインや予約の確保などの操作では、名前を送らず、置き換えもしない。2026-11-20 に要件の修正（USR-3・USR-7）に合わせて直した（2026-11-20 に開発者が確認）。
- **予約状況を見ること（USR-3, VIW-1）。** 見ることは「利用者として操作する」ことではない。共有された情報で利用を始めていれば、ログインの前でも予約状況（名前・期生・状態）を見られる。
