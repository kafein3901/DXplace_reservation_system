# 構成とデータの流れ

- 状態：決定
- 日付：2026-11-16
- 関係する要件：USR-1, USR-2, USR-3, ADM-2, ADM-3, RSV-21, RSV-22, RSV-23, RSV-24, RSV-27, SEC-1, PRE-5, NFR-4, FUT-1〜FUT-8
- 前提：[platform-selection.md](platform-selection.md)（データは DO の SQLite に置く前提。D1 に移せる形にする）

## 決定

### 1. 構成要素

```
ブラウザ（利用者の画面 / 管理者の画面）
   │  HTTPS
   ▼
Worker ─── 静的ファイル（public/）はそのまま返す
   │  /api/* はすべて転送
   ▼
Durable Object「台帳」（1つだけ）
   ├ 認証の確認（共有された情報・管理者）
   ├ 自動で起きる変化の反映
   ├ 入力の検証・ルールの判定
   └ SQLite（利用者・機器・予約・設定・管理者・記録・認証の状態）
```

| 要素 | 役割 | 持たないもの |
| --- | --- | --- |
| 画面（`public/`） | 入力を集めて API を呼び、結果を表示する。利用者として誰が操作しているか（USR-3）は、画面を開いている間だけ JavaScript の変数に持つ | ルールの判定、データ |
| Worker（`src/index.js`） | 静的ファイルを返す。`/api/*` を台帳にそのまま渡す | 判定、データ、認証の確認 |
| 台帳（Durable Object） | API の処理のすべて。1つのリクエストを、認証の確認から書き込みまで割り込まれずに行う | 画面 |

### 2. 台帳は1つにする

すべてのデータを1つの Durable Object に置き、すべての API をそこで処理する。

理由：

- RSV-23 が守らせる条件の多くは、機器をまたぐ。件数の上限（RSV-4）は全機器の予約を数え、機器の削除（MNG-2）や数値の変更（RSV-25）は予約と同時に起きうる。最後の1人の管理者（ADM-2）や、共有された情報の変更で全端末を止めること（ADM-3）もある。1か所で順に処理すれば、これらを考えずに済む。
- 認証の確認も台帳の中で行う。共有された情報の変更（ADM-3）や管理者の削除（ADM-2）の直後に、古い認証で操作が通ってしまう隙間をなくすため。
- NFR-3 の規模（10倍でも予約200件/日、同時200人）は、1つの DO で十分に処理できる。

### 3. 1つのリクエストの流れ

台帳の中で、すべての API が同じ順に処理する。例として予約の確保：

```
画面        POST /api/reservations（Cookie に利用開始の証明）
Worker      そのまま台帳へ
台帳   1. 現在時刻を1回だけ取る（以後この値を使う。TIM-1, TIM-6）
       2. 認証を確かめる（USR-1, USR-2。管理者の API なら ADM-2）
       3. 現在時刻までに自動で起きる変化を反映する（RSV-21, RSV-22）
       4. 入力の形式を確かめる（USR-4〜USR-6 など）
       5. ルールを判定する（RSV-3〜RSV-6 など）
       6. 書き込みと記録（LOG-1, LOG-3）を1つのトランザクションで行う
       7. 結果を返す。断るときは理由のコード（RSV-27）
```

- 2〜6 は同期的に行い、途中で `await` を挟まない。DO の SQLite は同期 API なので、これで他のリクエストが割り込まない（RSV-23）。PBKDF2（`await` が要る）は例外で、扱いは auth.md で決める。
- 3 を読むだけの API（空きの確認など）でも行う。定期処理がなくても、見た時点で正しい状態になる（RSV-21）。手順の中身は time-and-concurrency.md で決める。
- 断る理由のコードと応答の形は screens-and-api.md で決める。

### 4. コードの分け方

```
public/                 画面（ビルドしない。そのまま配る）
  index.html            利用者の画面
  admin.html            管理者の画面
  css/
  js/
src/
  index.js              Worker の入口。静的ファイルと /api の振り分けだけ
  ledger.js             Durable Object。リクエストを受け、上の 1〜7 を順に呼ぶ
  api/                  API ごとの処理（入力を取り出し、rules と store を呼ぶ）
  rules/                予約のルールの判定。純粋な関数
  store/                SQL はすべてここ
  lib/                  時刻、学籍番号の正規化、入力の検証、ハッシュ
test/                   src/ と同じ分け方
wrangler.jsonc
package.json
```

分け方の決まり：

| 場所 | 決まり | 理由 |
| --- | --- | --- |
| `rules/` | SQL も DO も `Date.now()` も使わない。必要なデータと現在時刻を引数で受け取り、「受け付ける」か「断る（理由のコード）」を返す | テストで時刻を差し替え、DB なしで速く確かめられる（NFR-4）。基盤を替えても書き直さずに済む |
| `store/` | SQL はここにだけ書く。他の場所はここの関数を呼ぶ | D1 に移すとき、直すのがここだけになる（platform-selection.md 未決事項1） |
| `api/` | 判定は `rules/` に任せ、自分では判定しない | ルールが1か所にまとまり、どこで断ったかを追いやすい |
| `public/` | 利用者の入力を `innerHTML` に入れない（`textContent` を使う） | SEC-1 |

### 5. 画面

- フレームワークもビルドも使わない。HTML / CSS / JavaScript をそのまま配る（PRE-5）。
- 利用者の画面と管理者の画面はファイルを分ける。入口を分ける ADM-2 に合わせる。
- 静的ファイルは、利用を始める前の人にも配る。中にデータを含めないので、USR-1（データを読み書きできない）には反しない。
- 画面での検証は使いやすさのためだけに行い、台帳で必ず確かめ直す（USR-1, RSV-24）。

### 6. 端末に持つもの

| もの | 置き場所 | 理由 |
| --- | --- | --- |
| 利用を始めたことの証明（USR-2） | Cookie（`HttpOnly`、`Secure`、`SameSite=Strict`） | 同じ端末で再入力しなくてよい。JavaScript から読めないので、仮に SEC-1 が破られても持ち出されにくい |
| 管理者の認証した状態（ADM-2） | Cookie（同上。名前は分ける） | 同上 |
| 利用者として誰か（USR-3） | 画面の JavaScript の変数だけ | v0.1.0 は端末に保存しない |

証明の中身（ランダムな値をハッシュで持つか、など）と止め方は auth.md で決める。

### 7. 将来の変更（9章）の受け入れ方

| ID | 受け入れ方 |
| --- | --- |
| FUT-1 | 画面の JavaScript で、API の失敗（停止）を見分けて表示する。静的ファイルは Worker の処理を通さずに配られる |
| FUT-2, FUT-3 | Worker に定期処理の入口（`scheduled`）を足す。台帳の構成は変わらない |
| FUT-4 | 記録を SQL で絞り込める表として持つ（logging.md）。確認画面は `admin.html` と `api/` に足す |
| FUT-5 | ルールは `rules/` に、自動で起きる変化の反映は手順 3 にまとまっているので、そこに条件と変化の種類を足す |
| FUT-6, FUT-7 | 台帳に表と API を足す。書ける人の判定は手順 2 の結果で分ける |
| FUT-8 | 画像は台帳とは別の置き場所にする（platform-selection.md）。見せる前の確認は、手順 2 と同じ認証を使う |

表の追加・変更に備え、台帳はスキーマの版を持ち、起動時に足りない変更だけを順に適用する。仕組みの詳細は詳細設計で決める。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 機器ごとに DO を分ける | 件数の上限（RSV-4）が機器をまたぐので、DO どうしの調整が要る。RSV-23 を守る仕組みが複雑になる |
| 認証の確認や入力の検証を Worker で行い、台帳には書き込みだけ渡す | 確認と書き込みの間に ADM-3 の変更などが割り込みうる。処理が2か所に分かれ、追いにくい |
| 読むだけの API は台帳を通さない | D1 などに分けないかぎり、データは台帳の中にしかない。自動で起きる変化の反映（手順 3）も台帳で行う必要がある |
| Worker から台帳を RPC（メソッド呼び出し）で呼ぶ | 振り分けが Worker と台帳の2か所になる。`Request` / `Response` のまま渡すほうが Web の一般的な知識で読める（PRE-5） |
| 画面にフレームワーク（React など）やビルドを使う | PRE-5。v0.1.0 の画面の量なら素の JavaScript で足りる |
| 利用者として誰かを `localStorage` に持つ | USR-3（v0.1.0 は端末に保存しない） |

## 残るリスク

- すべてのリクエストが1つの DO を通るので、DO が置かれた場所までの距離が応答時間に効く。最初に日本から作れば日本の近くに置かれる見込みだが、実測していない（platform-selection.md 未決事項3）。
- 外部からの大量のリクエストで台帳が詰まると、校内の利用者も使えなくなる。SEC-5 で許容している。
