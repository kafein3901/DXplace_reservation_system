# 時刻の扱い、自動で起きる変化、排他

- 状態：決定
- 日付：2026-11-16
- 関係する要件：TIM-1〜TIM-8, RSV-13, RSV-16, RSV-19, RSV-21〜RSV-23, RSV-26, ADM-2, ADM-3, NFR-4, FUT-5
- 前提：[architecture.md](architecture.md)（台帳は1つ。1つのリクエストを手順 1〜7 で処理する）、[domain-model.md](domain-model.md)（数値の設定は履歴で持つ）

## 決定

### 1. 時刻の表し方

| 決まり | 内容 | 要件 |
| --- | --- | --- |
| 持ち方 | すべての時刻を、1970-01-01 00:00 UTC からのミリ秒（整数）で持つ。JavaScript の `Date.now()` と同じ値 | ― |
| 境界の時刻 | 予約の開始・終了、数値の有効になる時刻は、60000（1分）の倍数だけを持つ | TIM-3 |
| 記録の時刻 | 実際の時刻（ミリ秒）のまま持つ。ただし自動の変化はルール上の時刻（分の倍数）になる | TIM-5, RSV-21 |
| 秒の切り捨て | `Math.floor(ms / 60000) * 60000` | TIM-4, TIM-6 |
| 日本時間 | 9時間（固定）を足して日付・時刻にする。日本に夏時間はないので、時期による違いはない | TIM-1 |
| 日の区切り | 日本時間の D 日は、[D 日 0:00, D+1 日 0:00) をミリ秒に直した範囲 | VIW-1, TIM-2 |

日本時間との差が時間単位なので、UTC で秒を切り捨てても日本時間で切り捨てても同じ結果になる。

日本時間との換算は `src/lib/time.js` だけで行う。API で時刻をどの形で受け渡すかは screens-and-api.md で決める。受け取った境界の時刻に秒以下があれば断る（TIM-3）。

画面に表示するときは、端末のタイムゾーンによらず日本時間で表示する（`timeZone: 'Asia/Tokyo'` を指定する）。画面の時計は表示にだけ使い、判定には使わない（TIM-1）。

### 2. 現在時刻

- 現在時刻は、`await` が要る準備（本文の読み取り、Cookie や共有された情報の SHA-256。auth.md 3）をすべて済ませた後、同期の区間（architecture.md 手順 2〜6）に入る直前に1回だけ取る。同じリクエストの中では、以後すべてこの値を使う。`blockConcurrencyWhile` で包む操作（下の 4）は、包んだ中で取る。
  - 理由：リクエストを受けた時点で取ると、その後の `await` の間に、後から来たリクエストが先に処理されうる。すると、遅い時刻の自動の変化が反映された後に、早い時刻の操作が処理される（RSV-22 に反する）。例：A が 10:14:59 に時刻を取って `await` し、B が 10:15:00 に来て先に処理され、10:15 に終わる利用中の予約を「終了」にする。その後 A が `nowMin` = 10:14 で予約なしの利用を始めると、10:14 にはまだ利用中だった機器に重ねて確保できてしまう。同期の区間の直前で取れば、処理の順と時刻の順がそろう。
- この値から2つを作る。
  - `now`：実際の時刻。記録の時刻と、操作した時刻に使う（TIM-5）。
  - `nowMin`：`now` の秒を切り捨てたもの。判定と、境界の時刻を決めるのに使う（TIM-4, TIM-6）。
- 台帳の処理の本体は、時計（現在時刻を返す関数）を引数で受け取る形にする（`handle(request, clock)`）。本体は、上の位置で `clock()` を1回だけ呼ぶ。本番では `fetch` が `Date.now` を渡し、テストは任意の時刻を返す関数（`() => t`）を渡す（下の 5）。時刻の値そのものを渡す形にしないのは、取る位置を本体の中で決めるため。

### 3. 自動で起きる変化の反映

台帳は、どのリクエストでも、認証と入力の形式を確かめた後に（architecture.md 手順 4）、`nowMin` までに起きるはずの変化をすべて反映する。読むだけのリクエストでも行う。

| 対象 | 起きる時刻（ルール上の時刻） | 変化 | 要件 |
| --- | --- | --- | --- |
| 予約済の予約 | 開始時刻＋猶予と終了時刻の、早いほう | 無断不使用 | RSV-13, RSV-16 |
| 利用中の予約 | 終了時刻 | 終了 | RSV-19 |

手順：

1. 予約済・利用中の予約のうち、起きる時刻が `nowMin` 以下のものを集める。
2. 起きる時刻の順（同じなら予約の番号の順）に並べ、1件ずつ状態を変え、ルール上の時刻で記録する（RSV-21）。
3. 1〜2 は、その後の操作と同じトランザクションで行う。

決めたことと理由：

- **「以下」で比べる。** 起きる時刻と同じ分に届いた操作は、変化の後に処理される。「同じ時刻では、自動の変化が操作より先に起きる」（RSV-22）を満たす。例：猶予が 10:15 に終わる予約に、10:15:30 に利用開始の操作が届いたら、先に無断不使用になり、操作は断られる。
- **猶予は開始時刻の時点の値。** 猶予の長さは、数値の履歴のうち、有効になる時刻が開始時刻以下で最も新しいものを使う（RSV-26、domain-model.md 3）。数値の変更は `nowMin` から有効になり、`nowMin` 以下に起きる変化はすでに反映済みなので、変更がそれより前の変化を変えることはない（RSV-22, RSV-25）。
- **反映した結果は書き込む。** 読むだけのリクエストでも状態を書き換え、記録を足す。書き込まずに、読むたびに見かけの状態を計算する案は、計算が2か所に分かれ、自動の変化の記録（LOG-3）も別に書く必要があるので採らない。
- **順に並べる。** v0.1.0 では、ある予約の変化がほかの予約の変化に影響しないので、順序は結果を変えない。それでも時刻順に並べて1件ずつ処理する形にしておく。FUT-5 でメンテナンスの開始・終了が加わると、順序が結果を左右するため（同じ時刻では時間帯の解放がメンテナンスの開始より先、メンテナンスの終了から猶予を数える、など）。そのときは、この並びに変化の種類と同じ時刻での優先順を足す。

6週間誰も使わなかった後でも、最初のリクエストでまとめて反映される（NFR-5）。

### 4. 排他（RSV-23）

#### 基本：`await` を挟まない

台帳はリクエストを1つずつ受けるが、処理の途中で `await` すると、その間に次のリクエストの処理が始まりうる。そこで、手順 2〜6（認証の確認から書き込みまで）を、`await` を挟まない同期的な処理として書く。DO の SQLite の API は同期的なので、これで書ける。

さらに手順 4〜6 を `ctx.storage.transactionSync()` の中で行う。途中で例外が起きたら、それまでの書き込み（自動の変化の反映を含む）がすべて取り消され、状態と記録が食い違わない。

#### 例外：ハッシュの計算

PBKDF2 は Web Crypto の非同期 API でしか計算できず、`await` が要る。しかも、データを確かめてからでないと計算できない。認証では、保存してあるソルトを読んでから計算する。アカウントの作成とパスワードの設定し直しではソルトを新しく作るので、値の上ではデータを読む前に計算できるが、試行の数と鍵（管理者の画面からなら管理者の認証）を確かめてから計算する。認証されていない相手に PBKDF2 の CPU を使わせないため（auth.md 7）。確かめてから書き込むまでの間に割り込まれないように、どの操作も包む（2026-11-19 に理由を直した。結論は変えていない）。対象は、管理者のパスワードを扱う操作（認証、アカウントの作成、パスワードの設定し直し。ADM-2）だけ。共有された情報は SHA-256 で、データを読む前に計算できるので対象にならない（auth.md 4）。

これらの操作は、処理全体を `ctx.blockConcurrencyWhile()` で包む。包んでいる間、台帳はほかのリクエストを受けないので、ハッシュの計算の前後でデータが変わらない。現在時刻も包んだ中で取る（上の 2）。

- 理由：ほかの操作と同じく「1つずつ順に」と考えればよく、読む人が割り込みを気にしなくて済む（PRE-5）。
- 代償：ハッシュの計算のあいだ（約30ms、最大44ms。auth.md 4）、ほかのリクエストが待たされる。NFR-3 の規模なら問題にならない。外部からの大量の試行で待ちが増える場合は、試行の制限（SEC-3）を、ハッシュを計算する前に確かめて減らす（auth.md）。
- 注意：包んだ処理が例外を投げると、台帳が作り直される。包んだ処理の中では例外を必ず受け止め、断る応答に変えて返す。

採らなかった案：ハッシュの計算の前と後で別々に同期的な処理を行い、後で「前に読んだ値が変わっていないか」を確かめ直す。待たせずに済むが、確かめ直す項目を操作ごとに漏れなく挙げる必要があり、誤りやすい。`blockConcurrencyWhile` で困ることが実測でわかったら、この案に替える。

### 5. テストでの時刻の差し替え（NFR-4）

| テストの対象 | 時刻の渡し方 |
| --- | --- |
| `src/rules/` | 関数の引数に任意の時刻を渡す。DB も DO も要らない |
| 台帳を通した動き（自動の変化の反映、記録、排他） | `@cloudflare/vitest-pool-workers` の `runInDurableObject` で台帳の中に入り、`handle(request, clock)` を任意の時刻を返す時計で呼ぶ |

本番の台帳に、時刻を差し替えるための入口（テスト用の API など）は作らない。外から時刻を操れると、ルールを回避できてしまう（RSV-24）。

## 採らなかった案

| 案 | 理由 |
| --- | --- |
| 時刻を「分」（整数）で持つ | 記録の時刻（TIM-5）はミリ秒が要り、単位が2つ混ざって取り違えやすい |
| 時刻を文字列（`2026-11-16T10:00+09:00` など）で持つ | 基盤の管理機能で読みやすいが、足し算・比較のたびに変換が要る。管理機能で見るときは SQL で日本時間に直せる（`datetime(列 / 1000, 'unixepoch', '+9 hours')`） |
| 日本時間の換算に `Intl` のタイムゾーン計算を使う | 日本は差が固定なので、足し算で足りる。読む人が `Intl` の仕様を知らなくてよい |
| 自動の変化を定期処理（Cron Triggers）で反映する | 定期処理の間の時刻に見た人には、反映されていない状態が見える（RSV-21）。見た時点の反映はどのみち要る |
| テスト用に時刻を差し替える API を本番に置く | RSV-24 |

## 確認したこと

- `blockConcurrencyWhile` は、台帳を作るとき以外（リクエストの処理の中）で使っても、文書どおりに動く（2026-11-18 に Cloudflare 上で実測。platform-selection.md 実測の結果）。台帳の中で1.5秒待つ間に、ほかの書き込みを5本送って確かめた。包まないと5本とも割り込み、包むと割り込みは0本で、ほかのリクエストは包んだ処理が終わるまで待った。
- 同じ実測で、PBKDF2 は `await` を書いても途中でほかのリクエストに順番を譲らなかった。ただ、これは仕様として書かれていないので、頼らずに `blockConcurrencyWhile` で包む。
