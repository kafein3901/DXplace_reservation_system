## 1. ファイルの分け方

```
public/
  index.html        利用者の画面
  admin.html        管理者の画面
  css/style.css     2つの HTML で共有する
  js/api.js         callApi だけ
  js/messages.js    コード → 文
  js/time.js        時刻の文字列の表示と足し引き
  js/user.js        利用者の画面の動き
  js/admin.js       管理者の画面の動き
  js/vendor/qrcode.js   qrcode-generator（管理者の画面だけで読む）
```

| ファイル | 中身 |
| --- | --- |
| `index.html`・`admin.html` | 画面（screens-and-api.md 1 の表の1行）ごとに `<section>` を1つ置き、`hidden` 属性を付け外しして切り替える。URL は変えない（screens-and-api.md 1）。上に画面を切り替えるボタンを並べる。項目の並びは HTML に書き、JS で作るのは一覧の行と選択肢だけ。`<html lang="ja">` と `viewport` の `meta` を付ける。入力欄には `<label>` を付ける |
| `css/style.css` | 2つの HTML で共有する1つのファイル。スマートフォンの幅に合わせた最小限の見た目 |
| `js/api.js` | `callApi(method, path, body)` だけ（下の 2.1） |
| `js/messages.js` | `messageFor(code, screen)` と、コードから文を引く表。表の中身と `screen` の扱いは 5 |
| `js/time.js` | 時刻の文字列から表示を作る関数（`11月20日 10:00`、日付付きの時間帯）と、`Date.UTC` での足し引き（2.8）。`user.js` と `admin.js` の両方が使うので分ける |
| `js/user.js`・`js/admin.js` | それぞれの画面の動き。利用者として誰か（USR-3）は `user.js` のモジュールの中の変数にだけ持つ（architecture.md 6） |
| `js/vendor/qrcode.js` | qrcode-generator（MIT ライセンス。auth.md 2） |

### 1.1 読み込み方

- 自分で書く JS は `<script type="module">` で読み、`import` / `export` でつなぐ。`index.html` は `user.js` を、`admin.html` は `admin.js` を読み、そこから `api.js`・`messages.js`・`time.js` を `import` する。NFR-1 のブラウザはすべて ES モジュールを読める。
- `vendor/qrcode.js` は配布物がグローバル変数（`qrcode`）を作る形なので、`admin.html` でふつうの `<script>` として `admin.js` より前に読む。
- 外部の CDN などからは何も読まない。すべて `public/` から配る。

### 1.2 qrcode-generator の版

- 版は 2.0.4（2025-08 公開。2026-11-19 時点の最新）に固定する。npm の配布物から、ブラウザでそのまま読めるファイルだけを `public/js/vendor/qrcode.js` に写す。
- ファイルの先頭に、ライブラリの名前・版・出典の URL・ライセンスをコメントで書く。版を上げるときは、ファイルを置き換え、このコメントとこの節を直す。
- 2.0.4 にブラウザでそのまま読める形（グローバル変数を作るファイル）がないとわかったら、実装のときに 1.4.4 を使い、この節を直す。描き方は 4.7。4.7 で使う `qrcode(typeNumber, errorCorrectionLevel)`・`addData`・`make`・`createDataURL(cellSize, margin)` が写した版にあることを、実装のときに確かめる。

## 2. 共通の動き

### 2.1 API の呼び方（`api.js`）

`callApi(method, path, body)` は、どの場合も次の2つの形のどちらかを返す（例外を投げない）。

| 場合 | 返す値 |
| --- | --- |
| `ok` が真の JSON | `{ ok: true, data }` |
| `ok` が偽で `error.code` がある JSON | `{ ok: false, code }` |
| 500（コードのない応答）、JSON として読めない応答（FUT-1 の基盤の停止など）、通信の失敗（`fetch` が失敗した） | `{ ok: false, code: null }` |

- `POST` は `Content-Type: application/json` を付け、本文を `JSON.stringify(body ?? {})` で送る。本文のない API でも `{}` を送る（api.md 2）。`GET` は本文を付けない。
- Cookie はブラウザが送る（同じオリジンの `fetch` の既定）。画面は Cookie に触れない（`HttpOnly`。architecture.md 6）。
- 応答の HTTP の状態コードではなく、本文の `ok` と `error.code` で分ける。HTTP はコードの頭から決まっている（error-codes.md 1）ので、画面が別に見る必要がない。

### 2.2 文の出し方（`messages.js`）

- `messageFor(code, screen)` が文を返す（`screen` の扱いは 5 の頭）。表にないコードと `null` には汎用の文を返す（error-codes.md 1）。
- 汎用の文は2つ。

| 場合 | 文 |
| --- | --- |
| `code` が `null`、または表にないコード | うまくいきませんでした。時間をおいてもう一度試してください。 |
| `NOT_FOUND_API` | 画面が古い可能性があります。再読み込みしてください。（api.md 5 の版の食い違い） |

- そのほかのコードの文は 5 の表に書く。

### 2.3 文を出す場所

- 画面（`<section>`）ごとに `.message` の要素を1つ置き、エラーの文も成功の文（例：「予約しました」）もここに出す。エラーか成功かは CSS のクラスで見分ける。
- 新しい文は前の文を置き換える。操作を始めたとき、画面を切り替えたときに消す。
- 文は `textContent` で入れる。

### 2.4 自動で画面を移るコード

どの API の応答でも、次のコードを受けたら画面を移り、移った先の `.message` に文を出す。ほかのコードは、その画面で文を出すだけ（画面ごとの読み直しは 2.8 と 3・4）。

| 画面 | コード | 移る先 |
| --- | --- | --- |
| 利用者 | `AUTH_REQUIRED`、`AUTH_REVOKED` | 利用の開始 |
| 利用者 | `NOT_FOUND_USER` | 利用者の入力（error-codes.md 3.4） |
| 管理者 | `AUTH_REQUIRED`、`AUTH_REVOKED` | 認証 |

`callApi` の呼び手ごとに書かず、`user.js`・`admin.js` の中で応答を受け取る1つの関数にまとめる。

### 2.5 開いたときの動き

**`index.html`**（auth.md 2、api.md 8.11、8.13）

1. URL に `#k=` があれば、値を取り出して `POST /api/session` に `{ k }` を送り、応答を待たずに `history.replaceState` で URL から `#` 以降を消す。成功なら予約状況の画面を出す。断られたら利用の開始の画面にコードの文を出す。
2. `#k=` がなければ `GET /api/session` を呼ぶ。`active` が真なら予約状況の画面を出す。偽なら利用の開始の画面に `reason` の文を出す。

**`admin.html`**（api.md 8.6）

1. `GET /api/admin/me` を呼ぶ。成功なら機器の画面を出す。`AUTH_REQUIRED`・`AUTH_REVOKED` なら認証の画面を出す（2.4）。

細部（`#k=` の値の取り出し方、利用の開始の画面の文の出し分け）は 3 で書く。

### 2.6 二重送信の防止

- 操作のボタンは、押してから応答が返るまで `disabled` にし、`finally` で戻す。止めるのは押したボタンだけ。
- ほかのボタンは止めない。同時に送られても台帳が1つずつ処理し、後のものは理由を付けて断られる（RSV-23）。

### 2.7 確かめ（`confirm()`）

取り消せない操作にだけ、送る前に `window.confirm()` で確かめる。`false` なら送らない。

| 確かめる | 確かめない |
| --- | --- |
| 予約の取消（利用者・管理者）、利用終了、管理者による終了、機器の削除、管理者の削除、共有された情報の変更 | 確保、予約なしの利用、利用開始、時間帯の変更、数値の変更、利用者の入力、管理者の作成、パスワードの設定し直し、機器の追加・名前の変更、管理者の認証を解く |

- 確かめないものは、誤っても同じ画面の操作で直せるか、取消で戻せる。
- 確かめの文は 3・4 で書く。影響の範囲を前もって示すこと（何件の予約が消えるか、など）は 10章で除かれているので、文に数を入れない。

### 2.8 表示の決まり

- **`innerHTML` を使わない（SEC-1）。** 静的な部分にも使わない。文字列は `textContent` で入れ、要素は `document.createElement` で作り、中身を消すときは `replaceChildren()` を使う。`innerHTML` が1か所もなければ、利用者の入力を HTML として入れる場所がないことを検索で確かめられる。
- **時刻は文字列のまま扱う（TIM-1）。** API の `YYYY-MM-DDTHH:mm`・`YYYY-MM-DD` は日本時間なので、文字列を切り分けて表示を作る（例：`2026-11-20T10:00` → `11月20日 10:00`）。`Date` で端末のタイムゾーンに直さない。
  - 時刻を足し引きする（例：終了時刻の初期値を開始の1時間後にする）ときは、日本時間の値をそのまま `Date.UTC` で作り、`getUTC*` で読み戻す。端末のタイムゾーンに左右されない。
  - `Date` から表示を作るときは `timeZone: 'Asia/Tokyo'` を付ける（screens-and-api.md 8）。
- **初期値は応答の `now` から作る（TIM-1）。** 日の初期値、時刻の入力の初期値、操作を出すかどうか（開始時刻の前か、など）は、直近の応答の `now`（利用者の機器の一覧 api.md 8.22、予約状況 8.24、自分の予約 8.29）から作る。`new Date()` で端末の時計を読まない。
- **操作の後は取り直す（VIW-3）。** 操作が成功したら、関係する一覧を API から取り直して描き直す。`NOT_FOUND_RESERVATION`・`NOT_FOUND_DEVICE`・`NOT_FOUND_ADMIN` と `STATE_*` を受けたときも、表示が古くなっているので文を出したうえで取り直す。どの一覧を取り直すかは 3・4 で書く。
- **ページを読み込み直さない。** 利用者として誰か（USR-3）が消えるため。読み込み直すのは利用者が自分でするときだけ（`NOT_FOUND_API` の文）。

### 2.9 画面での検証

- 送る前に確かめるのは、空の欄と、数で送る欄（期生・数値の設定）の値が数でないことだけ。当てはまれば送らずに `.message` に文を出す。
- 文字数、形式、時刻の前後などは確かめない。台帳が必ず確かめるので（USR-1、RSV-24）、画面で二重に持たない。ただし入力欄の `maxlength` などの HTML の属性は、打ち間違いを早く知らせるために付けてよい（各画面の節で書く）。

## 3. 利用者の画面

`index.html` の画面（screens-and-api.md 2）ごとに、項目・開いたときに呼ぶ API・操作と送る値・成功したとき・コードごとの動きを書く。2 の共通の動き（二重送信の防止、`textContent`、2.4 の自動の遷移、2.8 の取り直し）は繰り返さない。文は 5 の表から `messageFor` で引く。

### 3.1 全体

- **上の帯。** 「予約状況」「自分の予約」「利用者の入力」の3つのボタンと、操作する人の表示を置く。表示は、利用者を持っていれば「操作する人：山田（12期・生徒）」（教員は「山田（教員）」）、なければ「操作する人：未入力」。利用の開始の画面では帯を隠す（まだ何もできないため）。
- **利用者の変数。** `POST /api/me` の応答の `{ role, student_id, name, cohort }` を `user.js` のモジュールの変数に1つだけ持つ（USR-3、architecture.md 6）。なければ `null`。以後の操作の識別の組は、この `role`・`student_id`（そろえた値）を送る（api.md 8.16）。
- **選んでいる機器と日。** 予約状況で選んだ機器の番号と名前、日を変数に持ち、確保・予約なしの利用はその機器に対して行う（この2つの画面では機器を選び直さない）。
- **直近の `now`。** 8.22・8.24・8.29 の応答の `now` を1つの変数に上書きで持ち、初期値と出し分けはこれから作る（2.8）。
- **画面を出すたびに取り直す。** 予約状況と自分の予約は、その画面を出すたびに API を呼んで描き直す。ほかの画面で操作が成功した後に戻っても最新になるので、「自分の予約と予約状況を取り直す」（VIW-3）は、戻る先の画面を出すことで満たす。
- **移った先に文を出す順。** 画面を切り替えて `.message` を消し（2.3）、移った先に文を入れてから、取り直しを呼ぶ。取り直しは `.message` を消さない（2.3 の「操作を始めたとき」に当たらない）。取り直しが断られたときだけ、その文で置き換える。
- **利用者が要る画面。** 確保・予約なしの利用・自分の予約を出そうとして利用者の変数が `null` なら、行き先を覚えて利用者の入力を出す（screens-and-api.md 2）。入力が成功したら、覚えた行き先を出す。
- **時刻の表示。** `YYYY-MM-DDTHH:mm` を切り分けて `11月20日 10:00` の形にする（2.8）。予約状況の一覧だけは、選んだ日と同じ日の時刻を `10:00` と時刻だけで出す（3.4）。

### 3.2 利用の開始（USR-2）

- 項目：案内の文（`.message`）だけ。入力欄もボタンも置かない。値は QR コードの URL からだけ受け取る（auth.md 2）。
- 開いたときの動きは 2.5。`#k=` の値は `new URLSearchParams(location.hash.slice(1)).get('k')` で取り出す。`k` が空の文字列でもそのまま送り、台帳が `AUTH_SHARED_INFO_WRONG` で断る（画面で判定しない）。`#` があって `k` がなければ、`#k=` がないものとして 2.5 の 2 に進む。
- 成功したら予約状況を出す（3.4）。
- 文を出すコード：`AUTH_REQUIRED`（「QR コードを読んでください」）、`AUTH_REVOKED`、`AUTH_SHARED_INFO_UNSET`、`AUTH_SHARED_INFO_WRONG`、`LIMIT_ATTEMPTS`。`GET /api/session` の `active` が偽のときは `reason` のコードの文を出す（api.md 8.13）。
- ほかの画面で `AUTH_REQUIRED`・`AUTH_REVOKED` を受けて移ってきたときも（2.4）、そのコードの文を出す。利用者の変数は消さない（QR コードを読み直して開き直すと、どのみちページが読み込まれて消える）。

### 3.3 利用者の入力（USR-3〜USR-7）

項目（並びは段 1 の確かめる順と同じ。api.md 8.15）：

| 項目 | 欄 | 送る値 |
| --- | --- | --- |
| 生徒か教員か | ラジオボタン2つ（生徒・教員）。初めは選ばない | `role`：`student`・`teacher` |
| 学籍番号 | `type="text"`、`autocomplete="off"` | `student_id`：欄の値の前後の空白を `trim()` で除いた文字列 |
| 名前 | `type="text"`、`autocomplete="off"` | `name`：欄の値のまま（前後の空白は台帳が除く） |
| 期生 | `type="number"`、`min="1"`、`step="1"`。教員を選んでいる間は欄を `hidden` にする | `cohort`：`Number(欄の値)`。教員では送らない |
| 決定 | ボタン | ― |

- **画面での検証（2.9）。** 送る前に、生徒・教員が選ばれていない、学籍番号・名前が空、生徒で期生が空、期生が数でない（`Number.isFinite` でない）なら送らず、「〇〇を入れてください」「期生は数で入れてください」を出す。小数・0 などは送り、台帳の `INPUT_COHORT` に任せる。
- **学籍番号の前後の空白を画面で除く。** 貼り付けたときに付く空白で断られないようにするため（使いやすさのため。台帳は除かずに断る。rules.md 6.4）。全角・大文字は画面でそろえない（台帳がそろえる）。
- **欄の `maxlength` は付けない。** 名前の上限はコードポイントで数える（rules.md 6.2）が、`maxlength` は UTF-16 の単位で数えるので食い違う。学籍番号は生徒と教員で上限が違う。
- 成功したら、応答を利用者の変数に入れ（そろえた `student_id` を持つ。3.1）、学籍番号の欄も応答の値に置き換え、上の帯の表示を直す。覚えた行き先があればそこを出し、なければ予約状況を出す。移った先に「〇〇として操作します」と出す。
- 名前を置き換える前の確かめは置かない（10章、api.md 8.15）。
- 欄の値は画面を切り替えても消さない（`hidden` で隠すだけ）。別の人に切り替えるときは、この画面を開き直して入れ直す（USR-3）。
- 断られたら（`INPUT_ROLE`・`INPUT_STUDENT_ID`・`INPUT_NAME`・`INPUT_COHORT`）、この画面に文を出す。利用者の変数は変えない。
- ほかの画面で `NOT_FOUND_USER` を受けて移ってきたとき（2.4）は、利用者の変数を `null` にし、元の画面を行き先として覚える。欄には前の値が残っているので、そのまま決定し直せる。

### 3.4 機器の予約状況（VIW-1〜VIW-3）

項目：機器の選択（`<select>`）、日（`type="date"`）、「最新にする」ボタン、時間帯の一覧、「予約する」「予約なしで使い始める」ボタン。

開いたとき（この画面を出すたび。3.1）：

1. `GET /api/devices`（api.md 8.22）を呼び、選択肢を作り直し、`now` を持つ。
   - 機器が1つもなければ、一覧の場所に「機器がありません」と出し、2 に進まない。「予約する」「予約なしで使い始める」は `disabled` にする。
   - 選んでいた機器が選択肢にあればそれを、なければ最初の機器を選ぶ。
   - 日の欄が空なら、`now` の日（先頭の10文字）を入れる。空でなければ利用者が選んだ日を保つ。
2. `GET /api/devices/{id}/day?date=日` を呼び（api.md 8.24）、一覧を描き、`now` を持つ。

機器・日を変えたとき、「最新にする」を押したときは 2 だけを行う。日の欄が空なら送らずに「日を選んでください」と出す。

一覧の描き方：

- 1行は「時間帯 状態 名前（期生）」。例：`10:00–11:00 予約済 山田（12期）`。教員は名前だけ。名前は `textContent` で入れる（SEC-1）。学籍番号は応答にないので出せない（VIW-2）。
- 状態の文字：`reserved` は「予約済」、`in_use` は「利用中」、`finished` は「終了」、`admin_finished` は「管理者による終了」。前の2つ（確保済み）と後の2つ（利用があった時間帯）は CSS のクラスで色を分ける（VIW-1）。
- **日をまたぐ時間帯は切らない。** 選んだ日と違う日の端だけ、日付を付けて出す（例：`22:00–11月21日 02:00`）。
- 長さ0の利用（`start = end`）も `10:00–10:00 終了` として出す（rules.md 6.9）。
- **空き。** 選んだ日の範囲 `[日 00:00, 翌日 00:00)` から、確保済み（`reserved`・`in_use`）の時間帯を除いた残りを「空き」の行として、開始時刻の順に間に挟む（rules.md 6.9 で空きは画面が描くと決めた）。ただし、空きの始まりは `now` より前にしない。今日なら今より前は空きに出さず、過去の日には空きを出さない（過去の時刻は確保できない。TIM-6）。こうすると、利用があった時間帯（終わりはどれも `now` 以前）と空きは重ならない。
  - 計算は文字列の比較で行う。`YYYY-MM-DDTHH:mm` は同じ形どうしなら文字列の順と時刻の順が一致する。翌日の `00:00` は 2.8 の `Date.UTC` で作る。
- `slots` が空で空きもない（過去の日）なら「この日の予約はありません」と出す。

操作：

- 「予約する」：確保を出す（3.5）。利用者がなければ利用者の入力へ（3.1）。
- 「予約なしで使い始める」：予約なしの利用を出す（3.6）。同上。
- 機器が空いているかは画面で判定しない。空いていなければ台帳が `RULE_DEVICE_BUSY` で断る（RSV-24）。

コードごとの動き：`INPUT_DATE` は文を出すだけ。`NOT_FOUND_DEVICE` は文を出し、開いたときの 1 からやり直す（機器の選択肢を読み直す。2.8）。

### 3.5 確保（RSV-2〜RSV-6）

- 項目：機器の名前（選んでいる機器。`textContent`）、開始時刻・終了時刻（`type="datetime-local"`。刻みは既定の1分）、「予約する」「戻る」ボタン。
- 初期値（この画面を出すたび）：開始は「選んでいる日＋`now` の時刻」（今日なら `now` そのもの）、終了はその60分後（2.8 の `Date.UTC` で足す）。過去の日を選んでいれば過去の時刻になり、送れば `RULE_PAST` で断られる。
- 送る値：`POST /api/reservations` に `role`・`student_id`・`device_id`・`start`・`end`。`start`・`end` は欄の値（`YYYY-MM-DDTHH:mm`）をそのまま送る。どちらかが空なら送らずに「開始時刻と終了時刻を入れてください」と出す。
- 成功したら予約状況を出し、「予約しました」と出す（予約状況は出すときに取り直す。3.1）。
- 「戻る」は予約状況を出す。
- コードごとの動き：`INPUT_TIME`・`RULE_PAST`・`RULE_TIME_ORDER`・`RULE_LENGTH`・`RULE_COUNT`・`RULE_OVERLAP` は、この画面に文を出して欄を残す（直して送り直せる）。`RULE_PAST` は開始と終了のどちらかを示さない（台帳が区別しない。error-codes.md 3.6）。`NOT_FOUND_DEVICE` は予約状況を出して文を出す（機器の選択肢が読み直される）。

### 3.6 予約なしの利用（RSV-17, RSV-20）

- 項目：機器の名前、終了時刻（`type="datetime-local"`）、「使い始める」「戻る」ボタン。開始の欄は置かない（台帳が `nowMin` にする。api.md 8.27）。
- 初期値（この画面を出すたび）：終了は `now` の60分後。
- 送る値：`POST /api/walk-ins` に `role`・`student_id`・`device_id`・`end`。`end` が空なら送らずに「終了時刻を入れてください」と出す。
- 成功したら予約状況を出し、「使い始めました。使い終わったら「自分の予約」から利用終了してください」と出す。
- コードごとの動き：`INPUT_TIME`・`RULE_PAST`・`RULE_LENGTH`・`RULE_DEVICE_BUSY`・`RULE_OVERLAP` は、この画面に文を出す。`RULE_DEVICE_BUSY` の文には「自分の予約なら「自分の予約」から利用開始してください」を常に含める（自分の予約かどうかは画面ではわからない。応答に予約の持ち主はない）。`RULE_OVERLAP` は同じ機器の後の予約と重なるときで、終了時刻を早めれば通る（error-codes.md 3.6）。`NOT_FOUND_DEVICE` は 3.5 と同じ。

### 3.7 自分の予約（RSV-7〜RSV-19）

項目：「最新にする」ボタン、予約の一覧、時間帯の変更のフォーム（初めは `hidden`）。

開いたとき（この画面を出すたび。利用者が要る。3.1）・「最新にする」を押したとき：`POST /api/my/reservations`（api.md 8.29）に `role`・`student_id` を送り、一覧を描き、`now` を持つ。時間帯の変更のフォームは隠す。

一覧の描き方：

- 1行は「機器の名前 時間帯 状態」と操作のボタン。機器の名前は `textContent`（SEC-1）。時間帯は日付付き（`11月20日 10:00–11:00`。終わりが別の日なら終わりにも日付）。状態は「予約済」「利用中」。
- 予約がなければ「予約はありません」と出す。
- **操作のボタンは `status` だけで決める。**

| `status` | 出すボタン |
| --- | --- |
| `reserved` | 取消、時間帯の変更、利用開始 |
| `in_use` | 時間帯の変更、利用終了 |

- 利用開始は開始時刻より前でも出す。前倒しできるか（RSV-15 の重なりと長さ）は画面ではわからないので、台帳に任せる（RSV-24）。断られたら `RULE_BEGIN_OVERLAP`・`RULE_BEGIN_LENGTH` の文（「開始時刻になれば始められます」）が出る。
- 猶予を過ぎた予約済は、開いたときの一覧には出ない（台帳が反映してから引く。api.md 8.29）。

操作：

| ボタン | 確かめ（2.7） | 送る API | 成功したときの文 |
| --- | --- | --- | --- |
| 取消 | 「この予約を取り消しますか？」 | `POST /api/reservations/{id}/cancel` | 取り消しました |
| 利用開始 | なし | `POST /api/reservations/{id}/begin` | 利用を開始しました |
| 利用終了 | 「利用を終了しますか？」 | `POST /api/reservations/{id}/finish` | 利用を終了しました |
| 時間帯の変更 | なし | フォームを出す（下） | ― |

本文はどれも `role`・`student_id` だけ。成功したら文を出し、一覧を取り直す。予約状況は、次にその画面を出したときに取り直される（3.1）。

時間帯の変更のフォーム（RSV-9〜RSV-12）：

- 一覧の下に1つだけ置く。「時間帯の変更」を押すと、その予約の機器の名前と、開始・終了の欄（`type="datetime-local"`）、「変更する」「やめる」ボタンを出す。欄の初期値はその予約の今の `start`・`end`。
- **開始の欄を `disabled` にする場合**：`status` が `in_use`（RSV-10）、または `reserved` で `start <= now`（開始時刻を過ぎた猶予の中。RSV-11）。比べるのは 3.4 と同じく文字列どうし。欄の横に「開始時刻を過ぎているので、変えられるのは終了時刻だけです」と出す。
- 送る値：`POST /api/reservations/{id}/change` に `role`・`student_id`・`start`・`end`。変えない側も今の値を送る（`disabled` の欄も値を読んで送る。api.md 8.32）。欄が空なら送らない（2.9）。
- 成功したら「時間帯を変えました」と出し、フォームを隠して一覧を取り直す。両方とも変えずに決定しても成功する（台帳は何も書かない）。
- 「やめる」はフォームを隠す。
- 断られたら（`INPUT_TIME`・`RULE_START_PASSED`・`RULE_PAST`・`RULE_TIME_ORDER`・`RULE_LENGTH`・`RULE_OVERLAP`）、フォームを残して文を出す。`RULE_START_PASSED` は、画面を開いてから開始時刻を過ぎたときに届く。

コードごとの動き（どの操作でも）：`NOT_FOUND_RESERVATION`・`STATE_NOT_RESERVED`・`STATE_NOT_ACTIVE`・`STATE_NOT_IN_USE` は、文を出し、フォームを隠して一覧を取り直す（2.8）。文は取り直した後も消さない（取り直しで `.message` を消さない）。

## 4. 管理者の画面

`admin.html` の画面（screens-and-api.md 3）ごとに、3 と同じ項目で書く。2 の共通の動きは繰り返さない。文は 5 の表から `messageFor(code, 'admin')` で引く（5 の頭）。

### 4.1 全体

- **上の帯。** 「機器」「予約の管理」「数値」「管理者」「共有された情報」の5つのボタンと「認証を解く」のボタン、認証している管理者の表示（「管理者：田中（tanaka）」。`display_name`（`login_id`））を置く。認証の画面では帯を隠す。
- **管理者の変数。** `GET /api/admin/me`（api.md 8.6）か `POST /api/admin/login`（8.4）の応答の `{ id, login_id, display_name }` を `admin.js` のモジュールの変数に持つ。管理者の一覧で自分の行を見分けるのに `id` を使う（4.6）。認証の画面に移るときは `null` にする。
- **3.1 の決まりをそのまま使う。** 画面を出すたびに取り直す（機器・予約の管理・数値・管理者）、移った先に文を出す順、時刻の表示（`11月20日 10:00`）。
- **一覧の中の操作の行き先。** 一覧の行のボタンは、行の番号（`id`）をクロージャで持ち、パスに入れて送る。名前などの表示の値をパスや本文に使わない。
- **認証を解く（ADM-2）。** 確かめずに `POST /api/admin/logout` に `{}` を送る（認証し直せば戻れるので、2.7 の取り消せない操作に当たらない）。成功、または `AUTH_REQUIRED`・`AUTH_REVOKED`（すでに解かれていた。api.md 8.7）なら、管理者の変数を `null` にして認証の画面を出し、「認証を解きました」と出す。この2つのコードは 2.4 の自動の遷移より先にここで受ける。

### 4.2 認証（ADM-2）

- 項目：ID（`type="text"`、`autocomplete="username"`）、パスワード（`type="password"`、`autocomplete="current-password"`）、「認証する」ボタン。
- 送る値：`POST /api/admin/login` に `login_id`（欄の値の前後の空白を `trim()` で除いたもの。3.3 の学籍番号と同じ理由）・`password`（欄の値のまま）。どちらかが空なら送らない（2.9）。
- 成功したら、応答を管理者の変数に入れ、パスワードの欄を空にし、機器の画面を出す。
- 断られたら（`AUTH_ADMIN_FAILED`・`LIMIT_ATTEMPTS`）、この画面に文を出し、パスワードの欄を空にする。ID の欄は残す。`AUTH_ADMIN_FAILED` は ID とパスワードのどちらが違うかを示さない（台帳が区別しない。auth.md 8）。
- ほかの画面で `AUTH_REQUIRED`・`AUTH_REVOKED` を受けて移ってきたとき（2.4）は、そのコードの文を出す。

### 4.3 機器（MNG-1, MNG-2）

項目：追加のフォーム（名前の欄 `type="text"`、`autocomplete="off"`、「追加する」ボタン、欄の横に「30文字まで」）、機器の一覧、名前の変更のフォーム（初めは `hidden`）。

開いたとき（この画面を出すたび）：`GET /api/admin/devices`（api.md 8.18）を呼び、一覧を描く。名前の変更のフォームは隠す。

一覧の描き方：1行は「名前」と「名前の変更」「削除」のボタン。名前は `textContent`（SEC-1）。機器がなければ「機器がありません」と出す。

操作：

| ボタン | 確かめ（2.7） | 送る API と本文 | 成功したときの文 |
| --- | --- | --- | --- |
| 追加する | なし | `POST /api/admin/devices` に `{ name }`（欄の値のまま。前後の空白は台帳が除く） | 「〇〇」を追加しました（〇〇は応答の `name`） |
| 名前の変更 | なし | フォームを出す（下） | ― |
| 削除 | 「「〇〇」を削除しますか？ この機器の予約済の予約はすべて取り消されます。」 | `POST /api/admin/devices/{id}/delete` に `{}` | 「〇〇」を削除しました |

- 追加が成功したら、名前の欄を空にして一覧を取り直す。削除が成功したら一覧を取り直す。
- 名前の欄に `maxlength` は付けない（3.3 と同じく、`maxlength` は UTF-16 の単位で数え、台帳のコードポイントの数え方と食い違う。rules.md 6.6）。上限は欄の横の文で示す。
- 削除の確かめの文に件数は入れない（2.7）。予約済が取り消されること（MNG-2）は、件数によらず起きるので示す。

名前の変更のフォーム（MNG-1）：

- 一覧の下に1つだけ置く（3.7 の時間帯の変更のフォームと同じ形）。「名前の変更」を押すと、その機器の今の名前を初期値にした名前の欄と、「変更する」「やめる」ボタンを出す。
- 送る値：`POST /api/admin/devices/{id}/rename` に `{ name }`。欄が空なら送らない。
- 成功したら「名前を変えました」と出し、フォームを隠して一覧を取り直す。同じ名前のまま決定しても成功する（台帳は何も書かない。api.md 8.20）。
- 「やめる」はフォームを隠す。

コードごとの動き：`INPUT_DEVICE_NAME`・`RULE_DEVICE_NAME_DUPLICATE` は、文を出して欄を残す。`RULE_DEVICE_IN_USE` は文を出す（一覧は変わっていないので取り直さない）。`NOT_FOUND_DEVICE` は、文を出し、フォームを隠して一覧を取り直す（2.8）。

### 4.4 予約の管理（MNG-3）

項目：機器の選択（`<select>`）、「最新にする」ボタン、予約の一覧。

開いたとき（この画面を出すたび）：

1. `GET /api/admin/devices`（api.md 8.18）を呼び、選択肢を作り直す。機器が1つもなければ「機器がありません」と出し、2 に進まない。選んでいた機器が選択肢にあればそれを、なければ最初の機器を選ぶ（3.4 と同じ）。
2. `GET /api/admin/devices/{id}/reservations`（api.md 8.37）を呼び、一覧を描く。

機器を変えたとき、「最新にする」を押したときは 2 だけを行う。

一覧の描き方：

- 1行は「時間帯 状態 生徒か教員か 学籍番号 名前」と操作のボタン。例：`11月20日 10:00–11:00 予約済 生徒 12345678 山田`。時間帯は 3.7 と同じく日付付き。状態は「予約済」「利用中」、`role` は「生徒」「教員」。学籍番号と名前は `textContent`（SEC-1）。学籍番号は MNG-3 により出す（VIW-2 は管理者の画面には当てはまらない。api.md 8.37）。
- 予約がなければ「予約済・利用中の予約はありません」と出す。
- **操作のボタンは `status` だけで決める。** `reserved` には「取消」、`in_use` には「終了」。

操作：

| ボタン | 確かめ（2.7） | 送る API | 成功したときの文 |
| --- | --- | --- | --- |
| 取消 | 「この予約を取り消しますか？」 | `POST /api/admin/reservations/{id}/cancel` | 取り消しました |
| 終了 | 「この利用を終了させますか？」 | `POST /api/admin/reservations/{id}/finish` | 利用を終了させました |

本文はどれも `{}`。成功したら文を出し、一覧を取り直す（2 だけ）。

コードごとの動き：`NOT_FOUND_RESERVATION`・`STATE_NOT_RESERVED`・`STATE_NOT_IN_USE` は、文を出して一覧を取り直す（2.8。2 だけ）。`NOT_FOUND_DEVICE` は、文を出して開いたときの 1 からやり直す（機器の選択肢を読み直す）。

### 4.5 数値（RSV-25, RSV-26）

項目：3つの数値の行と、説明の文。1行は、名前・欄（`type="number"`、`min="1"`、`step="1"`）・単位・「保存」ボタン。

| 名前 | `key`（api.md 8.41） | 単位 |
| --- | --- | --- |
| 1人が同時に確保できる予約の件数の上限 | `max_count` | 件 |
| 利用開始の猶予 | `grace_minutes` | 分 |
| 1件の予約の長さの上限 | `max_length_minutes` | 分 |

- 説明の文（HTML に書く）：「変更は今から有効です。確保済みの予約は取り消されません。猶予は、それぞれの予約の開始時刻の時点の値が使われます。」（RSV-25, RSV-26）。管理者が変更の影響を読み違えないように置く。
- 開いたとき（この画面を出すたび）：`GET /api/admin/settings`（api.md 8.41）を呼び、3つの欄に入れる。
- 「保存」：その行の欄の値だけを送る（1回に1つ。api.md 8.42）。`POST /api/admin/settings` に `{ key, value: Number(欄の値) }`。欄が空、または `Number.isFinite` でないなら送らない（2.9。「〇〇を数で入れてください」）。小数・0 などは送り、台帳の `INPUT_SETTING_VALUE` に任せる。
- 成功したら「保存しました」と出し、応答の3つの値で3つの欄をすべて入れ直す（取り直さない。api.md 8.42）。同じ値のまま保存しても成功する。
- 断られたら（`INPUT_SETTING_VALUE`）、文を出して欄を残す。

### 4.6 管理者のアカウント（ADM-2）

項目：管理者の一覧、作成のフォーム、パスワードの設定し直しのフォーム（初めは `hidden`）、パスワードの案内の文。

- パスワードの案内の文（HTML に書く。auth.md 5）：「パスワードは15〜128文字の半角の英数字と記号です。人が考えた値は推測されやすいので、パスワード管理のアプリなどでランダムに作った値を使ってください。」

開いたとき（この画面を出すたび）：`GET /api/admin/admins`（api.md 8.44）を呼び、一覧を描く。設定し直しのフォームは隠す。

一覧の描き方：

- 1行は「名前（ID）」と操作のボタン。名前と ID は `textContent`（SEC-1）。
- 自分の行（`id` が管理者の変数の `id` と同じ）には「（自分）」を付け、「パスワードの設定し直し」を出さない（自分のパスワードは設定し直せない。api.md 8.46）。「削除」は出す（ADM-2）。
- ほかの行には「パスワードの設定し直し」「削除」を出す。

作成のフォーム：

| 項目 | 欄 | 送る値 |
| --- | --- | --- |
| ID | `type="text"`、`autocomplete="off"` | `login_id`：欄の値の前後の空白を `trim()` で除いた文字列（4.2 と同じ） |
| 名前 | `type="text"`、`autocomplete="off"` | `display_name`：欄の値のまま |
| パスワード | `type="password"`、`autocomplete="new-password"` | `password`：欄の値のまま |
| 作成する | ボタン | ― |

- `POST /api/admin/admins`（api.md 8.45）。どれかの欄が空なら送らない（2.9）。
- 成功したら「〇〇を作成しました。ID は △△ です」と出す（〇〇は応答の `display_name`、△△は応答の `login_id`。全角・大文字で入れても、そろえた値で認証することを示す。api.md 8.1）。3つの欄を空にして一覧を取り直す。
- 作った管理者のパスワードは、作った人がその管理者に画面の外で伝える。画面はパスワードを表示しない。

操作：

| ボタン | 確かめ（2.7） | 送る API と本文 | 成功したとき |
| --- | --- | --- | --- |
| パスワードの設定し直し | なし | フォームを出す（下） | ― |
| 削除（ほかの管理者） | 「〇〇（△△）を削除しますか？」 | `POST /api/admin/admins/{id}/delete` に `{}` | 「〇〇を削除しました」と出し、一覧を取り直す |
| 削除（自分） | 「自分のアカウントを削除しますか？ 削除すると、この画面の認証も解けます。」 | 同上 | 管理者の変数を `null` にして認証の画面を出し、「自分のアカウントを削除しました」と出す（api.md 8.47。応答で Cookie は消える） |

パスワードの設定し直しのフォーム（ADM-2）：

- 一覧の下に1つだけ置く。「パスワードの設定し直し」を押すと、対象の「名前（ID）」と、新しいパスワードの欄（`type="password"`、`autocomplete="new-password"`）、「設定する」「やめる」ボタンを出す。欄は空で出す。
- 送る値：`POST /api/admin/admins/{id}/reset-password` に `{ password }`（api.md 8.46）。欄が空なら送らない。
- 成功したら「〇〇のパスワードを設定し直しました。〇〇の認証はすべての端末で解けました」と出し、欄を空にしてフォームを隠し、一覧を取り直す（ADM-2。対象の証明は `AUTH_REVOKED` になる）。
- 「やめる」は欄を空にしてフォームを隠す。

コードごとの動き：

- `INPUT_LOGIN_ID`・`INPUT_NAME`・`INPUT_PASSWORD`・`RULE_ADMIN_ID_DUPLICATE` は、文を出して欄を残す。パスワードの欄も残す（直すのは ID や名前のことが多い。4.2 の認証で空にするのは、違うパスワードを打ち直させるため）。
- `RULE_ADMIN_LAST` は文を出す（一覧は変わっていないので取り直さない）。
- `RULE_ADMIN_SELF_RESET` は、自分の行にボタンを出さないのでふつうは届かない。届いたら文を出す（error-codes.md 3.6）。
- `NOT_FOUND_ADMIN` は、文を出し、フォームを隠して一覧を取り直す（2.8）。
- 断られたときも成功したときも、ほかの管理者の削除やパスワードの設定し直しで自分の認証は解けない。自分が別の管理者に削除・設定し直しをされていれば、次の要求で `AUTH_REVOKED` を受けて認証の画面に移る（2.4）。

### 4.7 共有された情報（ADM-3）

項目：説明の文、「設定・変更する」ボタン、QR コードの場所（`<img>`。初めは `hidden`）、URL の文字の場所（初めは `hidden`）。

- 説明の文（HTML に書く）：「押すと新しい値を作り、QR コードを表示します。今までの QR コードは使えなくなり、それで利用を始めた端末もすべて止まります。確保済みの予約は変わりません。QR コードはここで1回だけ表示されます。」（ADM-3、auth.md 2）
- 開いたとき：API を呼ばない（今の値を取り出す API はない。SEC-4）。前に作った QR コードが表示されていれば、そのまま残す（下）。
- 「設定・変更する」：確かめ「共有された情報を変更しますか？ 今までの QR コードは使えなくなります。」（2.7）。`POST /api/admin/shared-info` に `{}`（api.md 8.9）。最初の設定でも同じ文で確かめる（画面は未設定かどうかを知らない）。
- 成功したら：
  1. URL を `location.origin + '/#k=' + 応答の value` で作る（auth.md 2。利用者の画面は `index.html` で `/` から配る）。
  2. QR コードを描く：`qrcode(0, 'M')` で作り（型番は自動、誤り訂正は M）、`addData(URL)`、`make()` の後、`createDataURL(8, 4)`（1つの升を8ピクセル、余白4升）の値を `<img>` の `src` に入れる。`createImgTag`・`createSvgTag` は HTML の文字列を返すので使わない（2.8 の `innerHTML` を使わない決まり）。
  3. URL の文字を `textContent` で出す。カメラのない PC で開くとき（auth.md 2 の制約）と、手元の `wrangler dev` で手で確かめるとき（携帯から `localhost` は開けない）に、URL を写して開けるようにするため。
  4. 「設定しました。この QR コードを印刷するか、画像を保存してください。ページを閉じたり読み込み直したりすると、もう表示できません。」と出す。
- QR コードと URL は、ほかの画面に移っても消さない（`hidden` で隠すだけ）。ページを閉じる・読み込み直すと消える（値は `admin.js` の変数と `<img>` にだけある。auth.md 2 の「画面を閉じると、値はもうどこからも取り出せない」）。
- 断られたときは、前に表示していた QR コードを消さない（台帳は何も変えていないので、まだ使える）。コードは共通のもの（`AUTH_ORIGIN`・`AUTH_*`・`INPUT_BODY`）だけ。
- 応答が届かなかったとき（`code: null`）は、台帳では変わっている可能性があり、前の QR コードはもう使えないかもしれない。汎用の文を出し、前の QR コードは消す（古い値を正しいものとして掲示させないため。ADM-3「わからなくなったら設定し直す」）。

## 5. 文の一覧

`messages.js` の表の元。コード1つに文は1つで、利用者の画面と管理者の画面で共有する（2.2）。どちらの画面で出ても通じる文にする。汎用の文は 2.2。ここにないコード（`AUTH_ORIGIN` など、ふつうの操作では届かないもの）は汎用の文になる。

**画面の別。** `messageFor(code, screen)` の `screen` は `'user'`（既定）か `'admin'`。`'admin'` のときは先に 5.3 の管理者の画面の置き換えの表を引き、なければ共通の表（5.1・5.3）を引く。置き換えるのは `AUTH_REQUIRED`・`AUTH_REVOKED` の2つだけ（利用者は QR コードを読み直し、管理者は認証し直すので、案内が違う）。`user.js` は `messageFor(code)`、`admin.js` は `messageFor(code, 'admin')` を呼ぶ。

## 7. 採らなかった案

| 案 | 理由 |
| --- | --- |
| JS をグローバル変数と `<script defer>` でつなぐ | どのファイルが何に頼るかが読み取りにくい（PRE-5）。読む順を HTML の並びに頼ることになる |
| `innerHTML` にエスケープした文字列を入れる | エスケープを1か所でも忘れると SEC-1 が破れる。`innerHTML` を使わなければ、使っていないことを検索で確かめられる |
| `<dialog>` で確かめの画面を作る | コードが増える。`confirm()` で足りる（作り込まない方針） |
| HTML に1つだけメッセージの欄を置く | スマートフォンでは、操作した場所から見えないことがある |
| CSP のヘッダ（`_headers`）を付ける | 要件にない多重の対策で、設定のファイルが増える。SEC-1 は `textContent` で満たす |
| 送っている間、画面のすべてのボタンを止める | 台帳が1つずつ処理するので（RSV-23）、押したボタンを止めれば二重送信は防げる |
| 時刻を `Date` で端末のタイムゾーンに直して扱う | 端末の設定に左右され、TIM-1 に反しやすい |
| 画面での検証を台帳と同じだけ行う | 判定を2か所に持つことになり、食い違う。判定はサーバ側（RSV-24） |
| qrcode-generator を CDN から読む | 外部に頼り、版が知らずに変わりうる。管理者の画面で値を扱う（SEC-4）ので、外部のスクリプトを読まない |
| 予約状況の最初の日を端末の時計から作り、応答の `now` と違えば呼び直す | API は変えずに済むが、2.8 の「端末の時計を読まない」に例外ができる。`GET /api/devices` に `now` を足せば例外なしで済む（api.md 8.22） |
| 予約状況を時間軸の図で描く | 作り込まない方針に合わない。文字の一覧で VIW-1・VIW-2 を満たせる |
| 日をまたぐ時間帯を、選んだ日の範囲で切って出す | 一覧の形なら、もう一方の端に日付を付けて出すほうが簡単で、本当の時間帯を誤解しない |
| 利用開始のボタンを `now` と開始時刻で出し分ける | 前倒しできるか（RSV-15）は同じ機器の他の予約によるので、画面では判定できない。台帳に任せ、断られた理由を出す |
| `RULE_DEVICE_BUSY` のとき、自分の予約を引いて利用開始の案内を出し分ける | API の呼び出しが増える。案内を常に文に含めれば足りる |
| `RULE_PAST` で、入力と `now` からどちらの欄の誤りかを示す | 判定を画面に持つことになる（RSV-24）。1つの文で両方を案内できる |
| 学籍番号を画面で全角→半角・小文字にそろえて送る | そろえ方を2か所に持つことになる。前後の空白を除くだけにし、そろえるのは台帳（USR-4） |
| 名前の欄に `maxlength="30"` を付ける | `maxlength` は UTF-16 の単位で数え、台帳のコードポイントの数え方（rules.md 6.2）と食い違う |
| 確保・予約なしの利用の画面でも機器を選べるようにする | 予約状況で見た機器と違う機器を選び違えうる。予約状況で選んだ機器に限る |
| 管理者の画面では `messageFor` を通さず、`AUTH_REQUIRED`・`AUTH_REVOKED` の文を `admin.js` に書く | 文が2つのファイルに分かれ、文を直すときに探す場所が増える。`messages.js` に置き換えの表を持てば、文はすべて1か所にある |
| 利用者の画面と管理者の画面で `messages.js` を分ける | 共通のコード（`INPUT_BODY`・`NOT_FOUND_DEVICE` など）の文を2か所に持つことになる |
| 時刻の表示の関数を `user.js` と `admin.js` にそれぞれ書く | 同じ処理（2.8）を2か所に持つことになる。`time.js` を足す |
| 機器の名前の変更・パスワードの設定し直しを、一覧の行ごとの欄で行う | 行ごとに欄が並び、パスワードの欄が一覧に並ぶ。3.7 の時間帯の変更と同じく、一覧の下に1つのフォームを出す形にそろえる |
| 名前の変更・パスワードの入力に `window.prompt()` を使う | パスワードが伏せ字にならない。欄の初期値や `autocomplete` も付けられない |
| 自分の行にもパスワードの設定し直しのボタンを出し、`RULE_ADMIN_SELF_RESET` で断らせる | 必ず断られる操作を出すことになる。自分の行は `GET /api/admin/me` の `id` で見分けられる |
| 共有された情報の QR コードを `createImgTag`・`createSvgTag` で描く | HTML の文字列を返すので `innerHTML` が要る（2.8）。`createDataURL` を `<img>` の `src` に入れれば要らない |
| 共有された情報の QR コードを、ほかの画面に移ったら消す | 印刷や保存の前に移ると、変更し直すほかに戻す手段がない（ADM-3）。`hidden` で隠すだけにし、ページを閉じれば消える |
| 共有された情報の URL を文字で出さない | 文字で出すと人が打って使えるが、43文字のランダムな値で打つ手間は大きく、掲示の QR コードと同じく校内で共有する値である（auth.md 2）。出さないと、カメラのない PC や手元の `wrangler dev` で利用の開始を確かめられない |
| 数値の画面に、保存した値の履歴を出す | 要件の画面は「現在の値と変更」だけ（screens-and-api.md 3。api.md 8.41） |
