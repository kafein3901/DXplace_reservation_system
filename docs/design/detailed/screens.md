## 1. ファイルの分け方

```
public/
  index.html        利用者の画面
  admin.html        管理者の画面
  css/style.css     2つの HTML で共有する
  js/api.js         callApi だけ
  js/messages.js    コード → 文
  js/user.js        利用者の画面の動き
  js/admin.js       管理者の画面の動き
  js/vendor/qrcode.js   qrcode-generator（管理者の画面だけで読む）
```

| ファイル | 中身 |
| --- | --- |
| `index.html`・`admin.html` | 画面（screens-and-api.md 1 の表の1行）ごとに `<section>` を1つ置き、`hidden` 属性を付け外しして切り替える。URL は変えない（screens-and-api.md 1）。上に画面を切り替えるボタンを並べる。項目の並びは HTML に書き、JS で作るのは一覧の行と選択肢だけ。`<html lang="ja">` と `viewport` の `meta` を付ける。入力欄には `<label>` を付ける |
| `css/style.css` | 2つの HTML で共有する1つのファイル。スマートフォンの幅に合わせた最小限の見た目 |
| `js/api.js` | `callApi(method, path, body)` だけ（下の 2.1） |
| `js/messages.js` | `messageFor(code)` と、コードから文を引く表。表の中身は 5 で足す |
| `js/user.js`・`js/admin.js` | それぞれの画面の動き。利用者として誰か（USR-3）は `user.js` のモジュールの中の変数にだけ持つ（architecture.md 6） |
| `js/vendor/qrcode.js` | qrcode-generator（MIT ライセンス。auth.md 2） |

### 1.1 読み込み方

- 自分で書く JS は `<script type="module">` で読み、`import` / `export` でつなぐ。`index.html` は `user.js` を、`admin.html` は `admin.js` を読み、そこから `api.js`・`messages.js` を `import` する。NFR-1 のブラウザはすべて ES モジュールを読める。
- `vendor/qrcode.js` は配布物がグローバル変数（`qrcode`）を作る形なので、`admin.html` でふつうの `<script>` として `admin.js` より前に読む。
- 外部の CDN などからは何も読まない。すべて `public/` から配る。

### 1.2 qrcode-generator の版

- 版は 2.0.4（2025-08 公開。2026-11-19 時点の最新）に固定する。npm の配布物から、ブラウザでそのまま読めるファイルだけを `public/js/vendor/qrcode.js` に写す。
- ファイルの先頭に、ライブラリの名前・版・出典の URL・ライセンスをコメントで書く。版を上げるときは、ファイルを置き換え、このコメントとこの節を直す。
- 2.0.4 にブラウザでそのまま読める形（グローバル変数を作るファイル）がないとわかったら、実装のときに 1.4.4 を使い、この節を直す。描き方は管理者の画面（4）で書く。

## 2. 共通の動き

### 2.1 API の呼び方（`api.js`）

`callApi(method, path, body)` は、どの場合も次の2つの形のどちらかを返す（例外を投げない）。

| 場合 | 返す値 |
| --- | --- |
| `ok` が真の JSON | `{ ok: true, data }` |
| `ok` が偽で `error.code` がある JSON | `{ ok: false, code }` |
| 500（コードのない応答）、JSON として読めない応答（FUT-1 の基盤の停止など）、通信の失敗（`fetch` が失敗した） | `{ ok: false, code: null }` |

- `POST` は `Content-Type: application/json` を付け、本文を `JSON.stringify(body ?? {})` で送る。本文のない API でも `{}` を送る（api.md 2）。`GET` は本文を付けない。
- Cookie はブラウザが送る（同じオリジンの `fetch` の既定）。画面は Cookie に触れない（`HttpOnly`。architecture.md 6）。
- 応答の HTTP の状態コードではなく、本文の `ok` と `error.code` で分ける。HTTP はコードの頭から決まっている（error-codes.md 1）ので、画面が別に見る必要がない。

### 2.2 文の出し方（`messages.js`）

- `messageFor(code)` が文を返す。表にないコードと `null` には汎用の文を返す（error-codes.md 1）。
- 汎用の文は2つ。

| 場合 | 文 |
| --- | --- |
| `code` が `null`、または表にないコード | うまくいきませんでした。時間をおいてもう一度試してください。 |
| `NOT_FOUND_API` | 画面が古い可能性があります。再読み込みしてください。（api.md 5 の版の食い違い） |

- そのほかのコードの文は 5 の表に書く。

### 2.3 文を出す場所

- 画面（`<section>`）ごとに `.message` の要素を1つ置き、エラーの文も成功の文（例：「予約しました」）もここに出す。エラーか成功かは CSS のクラスで見分ける。
- 新しい文は前の文を置き換える。操作を始めたとき、画面を切り替えたときに消す。
- 文は `textContent` で入れる。

### 2.4 自動で画面を移るコード

どの API の応答でも、次のコードを受けたら画面を移り、移った先の `.message` に文を出す。ほかのコードは、その画面で文を出すだけ（画面ごとの読み直しは 2.8 と 3・4）。

| 画面 | コード | 移る先 |
| --- | --- | --- |
| 利用者 | `AUTH_REQUIRED`、`AUTH_REVOKED` | 利用の開始 |
| 利用者 | `NOT_FOUND_USER` | 利用者の入力（error-codes.md 3.4） |
| 管理者 | `AUTH_REQUIRED`、`AUTH_REVOKED` | 認証 |

`callApi` の呼び手ごとに書かず、`user.js`・`admin.js` の中で応答を受け取る1つの関数にまとめる。

### 2.5 開いたときの動き

**`index.html`**（auth.md 2、api.md 8.11、8.13）

1. URL に `#k=` があれば、値を取り出して `POST /api/session` に `{ k }` を送り、応答を待たずに `history.replaceState` で URL から `#` 以降を消す。成功なら予約状況の画面を出す。断られたら利用の開始の画面にコードの文を出す。
2. `#k=` がなければ `GET /api/session` を呼ぶ。`active` が真なら予約状況の画面を出す。偽なら利用の開始の画面に `reason` の文を出す。

**`admin.html`**（api.md 8.6）

1. `GET /api/admin/me` を呼ぶ。成功なら機器の画面を出す。`AUTH_REQUIRED`・`AUTH_REVOKED` なら認証の画面を出す（2.4）。

細部（`#k=` の値の取り出し方、利用の開始の画面の文の出し分け）は 3 で書く。

### 2.6 二重送信の防止

- 操作のボタンは、押してから応答が返るまで `disabled` にし、`finally` で戻す。止めるのは押したボタンだけ。
- ほかのボタンは止めない。同時に送られても台帳が1つずつ処理し、後のものは理由を付けて断られる（RSV-23）。

### 2.7 確かめ（`confirm()`）

取り消せない操作にだけ、送る前に `window.confirm()` で確かめる。`false` なら送らない。

| 確かめる | 確かめない |
| --- | --- |
| 予約の取消（利用者・管理者）、利用終了、管理者による終了、機器の削除、管理者の削除、共有された情報の変更 | 確保、予約なしの利用、利用開始、時間帯の変更、数値の変更、利用者の入力、管理者の作成、パスワードの設定し直し |

- 確かめないものは、誤っても同じ画面の操作で直せるか、取消で戻せる。
- 確かめの文は 3・4 で書く。影響の範囲を前もって示すこと（何件の予約が消えるか、など）は 10章で除かれているので、文に数を入れない。

### 2.8 表示の決まり

- **`innerHTML` を使わない（SEC-1）。** 静的な部分にも使わない。文字列は `textContent` で入れ、要素は `document.createElement` で作り、中身を消すときは `replaceChildren()` を使う。`innerHTML` が1か所もなければ、利用者の入力を HTML として入れる場所がないことを検索で確かめられる。
- **時刻は文字列のまま扱う（TIM-1）。** API の `YYYY-MM-DDTHH:mm`・`YYYY-MM-DD` は日本時間なので、文字列を切り分けて表示を作る（例：`2026-11-20T10:00` → `11月20日 10:00`）。`Date` で端末のタイムゾーンに直さない。
  - 時刻を足し引きする（例：終了時刻の初期値を開始の1時間後にする）ときは、日本時間の値をそのまま `Date.UTC` で作り、`getUTC*` で読み戻す。端末のタイムゾーンに左右されない。
  - `Date` から表示を作るときは `timeZone: 'Asia/Tokyo'` を付ける（screens-and-api.md 8）。
- **初期値は応答の `now` から作る（TIM-1）。** 日の初期値、時刻の入力の初期値、操作を出すかどうか（開始時刻の前か、など）は、直近の応答の `now`（予約状況 api.md 8.24、自分の予約 8.29）から作る。`new Date()` で端末の時計を読まない。
- **操作の後は取り直す（VIW-3）。** 操作が成功したら、関係する一覧を API から取り直して描き直す。`NOT_FOUND_RESERVATION`・`NOT_FOUND_DEVICE`・`NOT_FOUND_ADMIN` と `STATE_*` を受けたときも、表示が古くなっているので文を出したうえで取り直す。どの一覧を取り直すかは 3・4 で書く。
- **ページを読み込み直さない。** 利用者として誰か（USR-3）が消えるため。読み込み直すのは利用者が自分でするときだけ（`NOT_FOUND_API` の文）。

### 2.9 画面での検証

- 送る前に確かめるのは、空の欄と、数で送る欄（期生・数値の設定）の値が数でないことだけ。当てはまれば送らずに `.message` に文を出す。
- 文字数、形式、時刻の前後などは確かめない。台帳が必ず確かめるので（USR-1、RSV-24）、画面で二重に持たない。ただし入力欄の `maxlength` などの HTML の属性は、打ち間違いを早く知らせるために付けてよい（各画面の節で書く）。

## 7. 採らなかった案

| 案 | 理由 |
| --- | --- |
| JS をグローバル変数と `<script defer>` でつなぐ | どのファイルが何に頼るかが読み取りにくい（PRE-5）。読む順を HTML の並びに頼ることになる |
| `innerHTML` にエスケープした文字列を入れる | エスケープを1か所でも忘れると SEC-1 が破れる。`innerHTML` を使わなければ、使っていないことを検索で確かめられる |
| `<dialog>` で確かめの画面を作る | コードが増える。`confirm()` で足りる（作り込まない方針） |
| HTML に1つだけメッセージの欄を置く | スマートフォンでは、操作した場所から見えないことがある |
| CSP のヘッダ（`_headers`）を付ける | 要件にない多重の対策で、設定のファイルが増える。SEC-1 は `textContent` で満たす |
| 送っている間、画面のすべてのボタンを止める | 台帳が1つずつ処理するので（RSV-23）、押したボタンを止めれば二重送信は防げる |
| 時刻を `Date` で端末のタイムゾーンに直して扱う | 端末の設定に左右され、TIM-1 に反しやすい |
| 画面での検証を台帳と同じだけ行う | 判定を2か所に持つことになり、食い違う。判定はサーバ側（RSV-24） |
| qrcode-generator を CDN から読む | 外部に頼り、版が知らずに変わりうる。管理者の画面で値を扱う（SEC-4）ので、外部のスクリプトを読まない |
